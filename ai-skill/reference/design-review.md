# 策划自审 + 测试审查（**动手前必做、交付前必跑**）

> 这份文档解决一个**只有人才能发现、编译器和测试都抓不到**的问题：
> 代码能跑、日志全绿，但**玩家一看就觉得不是个游戏** —— 
> 动画接不上、攻击没反馈、敌人没血条、血条恒满、镜头乱转、占位几何体当角色。
> 一句话：**逻辑错误靠测试，感官错误靠"先想清楚该是什么样"，再逐条演一遍。**

---

## 1. 策划自审：先回答"这是个什么游戏"，再写代码

**动手前必须能回答下面 6 问**（答不出就先搜、先问，不许凭感觉动手）：

1. **这是什么游戏？**（类型 + 参考游戏：例如"3D 第三人称 MMO 拆解：移动 + 近战 + 假人靶子"）
2. **玩家从打开游戏到开始玩，要经过哪些界面？**（启动画面 → 主菜单 → 创角 / 选角 → 读条进图；**没有完整游戏是直接进游戏场景的** —— 这一段见 `patterns/client/app-flow.md`）
3. **玩家现在在做什么？**（一局的核心循环：进图 → 走动看世界 → 打怪 → 被打 → 复活 → 继续）
4. **每个行为*应该*看到/听到什么？**（→ 填成第 2 节的表）
5. **数值与节奏是什么？**（跑速、攻击范围、几下打死、冷却、死亡到复活多久）
6. **哪些"不行"算设计内？**（撞墙不能穿、打不到的提示、死亡不能动）

> **不知道规格就去搜**：参考游戏的手感/表现（搜"reference game + 该行为"）、
> 官方文档、同类型项目的截图/视频。**搜不到就把"我不确定"写进规格里并问用户** —— 
> 唯一不允许的是"我觉得差不多就行"。

### 反面教材（都真实发生过）

| 糊弄的写法 | 玩家的感受 |
| --- | --- |
| 用内置胶囊体当角色 | "这游戏是半成品吧" |
| 动画只在日志里切状态、或状态机根本没接好 | "跑起来像在滑步/一直播同一个动作" |
| 攻击只播动画、不判命中、不转身、无飘字无音效 | "攻击打不到人" |
| 血条恒满 / 敌人没有血条 | "根本不知道打没打中、打了多少" |
| "动画留钩子，后续替换" | "哪哪都不对" |

## 2. 核心产出：《行为 → 表现规格》表（做之前写，验收时逐条打勾）

**每个功能动手前，先把它的每个通道填满**（空白格 = 你还没想清楚，不许开工）：

| 行为 | 触发 | 画面 | 动画 | 声音 | UI / 数值反馈 | 验收方法（怎么证） |
| --- | --- | --- | --- | --- | --- | --- |
| 走动 | WASD | 角色在世界里位移，镜头跟随 | Idle → Run（**平滑过渡，不跳帧**） | 脚步（按步频） | HUD：意图/实际速度 | 自证脚本 + 截图 + 位移算术 |
| 攻击 | F / 左键 | 挥砍动作，角色**转向目标** | Attack（播完回 Idle） | 挥砍音 | 命中后目标**飘字 -19**、目标**血条下降** | 服务端日志 + 客户端飘字 |
| 受击 | 被命中 | 目标闪一下/受击动作 | Hit | 命中音（3D 定位） | 自己血条下降 + 数字 | 逐条日志 |
| 死亡 | HP=0 | 倒地、遮罩、禁用操作 | Death | 低沉音 | 「按 R 复活」 | 截图取证 |
| 复活 | R | 回出生点、满血 | Idle | 进图音 | 血条回满 | 日志 + 自证 |
| 敌人 | 刷假人 | 真模型（**不是占位球**）+ 头顶**血条** | Idle/Run 随移动切换 | 受击音 | 头顶血条随伤害下降 | 自证：敌人数/模型数/血条数一致 |

**硬要求**：

- 表里出现"占位 / 后续替换 / 留钩子"字样 ⇒ 视为**没做完**，不得交付；
- 每行都要有**可执行的验收方法**（自证脚本 / 探针 / 截图 / 日志），不能是"看着对"；
- 参考游戏能搜到的，就把"保真项"写进表里（手感/节奏/镜头/音效时机）。

## 3. 测试审查：交付前逐条"演一遍"（不是看代码）

> 规则：**每个功能都要有人（AI 自己）在 Play 里跑过并留下证据**。代码对不对 ≠ 玩起来对不对。

### 3.1 感官项必查清单（缺一项就不算过）

| # | 项 | 怎么查 | 不合格的样子 |
| --- | --- | --- | --- |
| 1 | **动画衔接** | 走动时读 `Animator` 当前状态名（`IsName("Run")`）+ `GetCurrentAnimatorClipInfo` | 一直播第一个动画 / 状态在 Idle 与 Run 之间抖 / 过渡跳帧 |
| 2 | **转身** | 反向走动、攻击时观察朝向 | 平移不转身 / 攻击不朝向目标 |
| 3 | **命中反馈** | 打一下，看**飘字 + 音效 + 目标血条**三件套 | 只有动画、打完没感觉 |
| 4 | **血条** | 自己被打 / 打敌人 | 恒满 / 不显示数字 / 敌人没有血条 |
| 5 | **镜头** | 贴墙、贴脸、跑动、跳 | 穿墙 / 抖动 / 被角色挡满屏 |
| 6 | **音效时机** | 脚步、挥砍、命中、UI、进图 | 无声 / 时机错（先响后打）/ 每帧狂响 |
| 7 | **死亡与复活** | 真的被打死 → 按 R | 死了还能动 / 复活后血条不满 / 没遮罩 |
| 8 | **占位物** | 扫一眼场景 | 胶囊体/橙色小球当敌人（占位没被替换或没被隐藏） |
| 9 | **数值自洽** | 打几下死、跑多久到 | 一下秒杀 / 打半天不死 / 速度对不上 |
| 10 | **流程链路** | 从启动画面一路点到进图，再暂停 → 回主菜单 → **再进一次** | 直接进游戏场景 / 菜单项点了没反应 / 返回是死路 / 第二次进图状态残留（实体、订阅没清） |

### 3.2 交互项

- **菜单链路每个界面都要点一遍**：启动 / 主菜单 / 创角（或选角）/ 读条 / 游戏内 / 暂停 / 结算 —— 每个按钮都点过，每个界面都有返回路径；
- 键位全覆盖（每个键都按过一遍）；UI 按钮都能点、点了有回应；
- 边界：撞墙、出图、断线、重连、重复进图、同账号顶号；
- **连打/连点**不会刷屏、不会打空日志、不会状态错乱。

### 3.5 ★ 文档/注释对齐审计（定期做，别等出事）

> 文档比代码"烂得更快"：代码改名/搬家，文档里的名字会一直躺着，而且**看起来特别可信**。
> 更要命的是"照着写就编译不过"的那类 —— 必须靠审计抓，不能靠感觉。

**审计做法（可复用）**：把 skill/文档里的**具体断言**逐条抽出来（API 名、签名、文件路径、目录约定、常量、行为描述），
去引擎源码里找证据，逐条判：`一致 / 不存在 / 名字不符 / 路径不符 / 无法证实`，落到 `文件:行`。
（本仓真的跑过一轮：两路只读审计 + 逐条复核，见下表。）

**本轮抓到的典型漂移（按危害排序）**：

| 类型 | 例子 | 危害 |
|---|---|---|
| **名字不符（编译不过）** | 文档写 `MsgContext`（引擎是 `NetCtx`）、`IEIPanel`（是 `IUIPanel`）、`ELoginReply{PlayerID:...}`（该结构体没有这个字段） | 照抄 → **编译失败 / 逻辑错** |
| **路径不符（静默失效）** | 音效写成 `Resources/Audio/`（引擎实际读 `Sound/SFX/{名}`） | 文件放对了也不响，**不报错** |
| **断言与源码相反** | 说 `Game.Logger` 启动前为 null（实际 `= ConsoleLogger.Instance`，永不为 null） | 让业务到处加 `?.`、甚至自建日志兜底 |
| **API 不存在** | `mmo.NewWorld` / `aoi.New()` / `proto.EMsgCreatePlayer`（真入口是 `mmo.NewSceneManager` / `mmo.NewGrid`） | 到处搜不到，白耗时间 |
| **引用已删除的东西** | 断言 demo `function_test/state_room.go`"已是成品"（随 `clover-demo-a` 一起删了） | 让人以为有现成品可抄 |
| **文档自相矛盾** | 一处"回包不占消息号"，另一处又给 `XxxReply = 2000101` | 新人不确定该听谁的 |

**三条结论性约定（已固化到本 skill 各文档）**：

1. **回包不占消息号**：只写回包**结构体**，用 `Call<T>` 按 requestID 配对，**不定义** `XxxReply` 常量；
2. **引擎 API 名字改了就全局搜**：审计时用「旧名全文 grep → 命中归零」当验收方式（比"我改过了"可靠）；
3. **引擎注释也算文档**：引擎源码里解释"为什么这么写"的注释若与现状相反（如 logger 兜底），
   一并订正 —— 否则下次还会被自己的旧注释骗。

### 3.4 ★ 看图验收：数字会骗人，截图不会

> **自证输出全对、日志全绿，画面仍然可以是错的。** 这一条是拿真事故换来的：

| 只看数字（会漏） | 自己看图（立刻发现） |
| --- | --- |
| `hp=82/100`、血条组件存在、`fillAmount` 有赋值 ⇒ "血条正常" | 截图里血条是**一整条深红、永不变化** —— `Image.Type.Filled` 但 **sprite 为空**时 `fillAmount` 静默失效（Unity 的经典坑） |
| `withModel=4`、`材质=knight_texture` ⇒ "模型正常" | 截图里角色**全身纯白** —— 调色板贴图没跟着 FBX 进 Resources（Unity 按"**材质名 = 贴图名、同目录**"关联），材质在但 `mainTexture=空` |
| `敌人血条=True` ⇒ "血条有了" | 截图里血条只有**一条发丝那么细**，1600×900 下根本看不清 ⇒ 尺寸也要验收 |

**做法（硬性）**：

> **采集形态 = 联络图**（`reference/visual-loop.md` 第八节）：把要看的点排进**证据分格表** →
> **一条驱动链路跑完、只采一次** → **脚本按格判定**（diff / 断言）→ **AI 只读那张汇总图一次** →
> 只有 `FAIL` 的格才去看那一格的原始大图。⛔ 不逐项进出 Play、不逐张读原图。

1. `表现类` 的项进联络图后，对照《行为→表现规格》**逐格**读结论；
2. 至少检查：角色是否**有贴图**（不是纯白/纯灰）、血条**有没有随数值变化**、UI 元素**大小/位置是否可读**、有没有残留占位物；
3. 某格看不出来 / 有疑问 ⇒ **只看那一格**（单独放大或重截那一处），⛔ 不用把整批重采一遍；
4. 图与数字冲突时，**以图为准**，然后去查为什么数字对而画面不对（通常是"组件在但参数无效"这类静默失效）。

### 3.6 ★ 参考游戏对照审查（**交付闸门：不像 = 不可交付**）

> **"跑通了"不等于"可以交付"。** 交付前必须把成品和**参考游戏**并排比一遍；**只要不像，这个版本就不可交付** —— 不许汇报完成，改到一样为止。

**前置：必须有参考游戏名。** 用户没给 → **停下来问用户"参照哪款游戏"**（可给 2~3 个同品类候选让用户挑，**不许自己拍板**）。禁止"我自己挑个同类型的吧"。

**做法**：

1. **配对**：参考游戏的截图（启动 / 主菜单 / 创角 / HUD / 战斗 / 场景 / 结算）+ 自己的**同角度**画面，一一配对，存 `策划/参考图/` 与 `策划/自审对比/` ——
   **采集形态与判定见 `reference/visual-loop.md` 第八节**（联络图：一条链路采一次、脚本按格判定、AI 只读汇总图一次）；
2. **逐项对照并写结论**（**只允许 `一致` / `不一致（差在哪）`，不许"基本一致 / 大致像"**）：

| 维度 | 对照什么 |
|---|---|
| 启动 / 菜单 | 界面数量与层级、按钮文案与位置、背景与配色 |
| 创角 / 选角 | 字段与选项、布局、确认 / 返回路径 |
| HUD | 血条 / 资源 / 技能栏 / 小地图的位置、比例、颜色、字号层级 |
| 手感 | 移动速度、转身、攻击节奏、镜头 FOV 与跟随、后坐力 / 硬直 |
| 表现 | 动画状态切换、命中反馈三件套（飘字 + 音效 + 目标血条）、特效 |
| 场景 | 地图风格、地形、光照、色调 |
| 音效 | BGM / 点击 / 命中 / 进图 的时机与音量层级 |
| 节奏 | 一段 / 一局时长、死亡复活、结算时机 |

3. **判定规则（硬）**：**任何一项 `不一致` ⇒ 该版本不可交付** → 改 → 重新截图 → 重新对照，**循环到全部一致**；
4. **必须看图**（§3.4）：数字全对但画面不像 = 不合格；
5. **禁止免责式交付**："基本一致 / 略有差异 / 后续可优化 / 剩余项列入清单" 一律视为**没做完**。

**输出留痕**：`策划/自审对比/` 下的配对截图 + 一张逐项结论表（每项 `一致` / `不一致(差在哪)`）。

### 3.3 审查输出（必须留痕）

```text
① 《行为→表现规格》表（逐条打勾 + 证据）
② 感官项 10 条逐项结论（通过/不通过 + 证据）
③ 不通过项 → 当轮修掉；确实做不了的 → 写进《资源欠缺清单》并说明为什么
④ 截图 / 自证输出 / 服务端日志（可回查）
⑤ ★ 参考游戏对照表（§3.6）：每项 `一致` / `不一致(差在哪)`；**有任一不一致 ⇒ 不可交付**
⑥ `策划/自审对比/` 的配对截图（参考图 ↔ 自己的截图）
```

## 4. 和"铁律"的关系

- **铁律 11**：动手前先出《行为→表现规格》（策划自审）；
- **铁律 12**：交付前逐条对照规格做测试审查，感官项必须自己跑过并留证据；
- **铁律 16**：交付前必须自审「像不像参考游戏」（本文件 §3.6）—— **不像 = 不可交付**；没有参考游戏名就先问用户要。

> 这两条与"一次做完"是同一件事的两面：**一次做完 ≠ 一次写完**，
> 而是"把这张表填满、把它演对"。填不满就先搜、先问，别先把代码堆出来。
