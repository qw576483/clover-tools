# 一键出游戏：交付标准与自审（用到时再查）

> 本文是**能力/详述**，不是规则。规则原文在 `SKILL.md::第一铁律`、`SKILL.md::一键出游戏`（各只有几行）。
> 这里讲"交付物长什么样、清单怎么列、自审怎么打分"。**动手做游戏时读一次即可。**

---

## 0. 三段式交付（缺任一段 = 没交付）

> **这不是"最小可用版本"，也不是"先交个骨架看看"。** 用户说"做一个 XX"，要的是**和原版一模一样的最终品**：
> **从启动到进游戏的一整套链路 + 首场景的全部系统**，每一项都按原版做，表现/手感都要像原版。

| 段 | 内容 | 缺了会怎样 |
|---|---|---|
| **① 启动与菜单链路** | 启动画面 / Logo → 主菜单（开始 / 继续 / 设置 / 退出；联机含登录、注册）→ **创角（或选角）** → 读条进图 | **世界上没有一个完整游戏是"打开就直接站在游戏场景里"的** —— 没这条链路 = 一眼假，用户不会用 |
| **② 首场景 / 首关卡完整版** | 场景与地图、操作与相机、动画、UI/HUD、战斗闭环、音效、复活、结算 | 能跑但不能玩 = 半成品 |
| **③ 游戏内流程** | 暂停菜单、设置、结算界面、回主菜单、退出 | 进去出不来 = 死路 |

**按原版列清单、逐项做完（禁止砍）**：动手前先把 A 的**系统清单**写出来，一行一个系统，**空着的行就是没做完**。

- 例（超级马里奥兄弟 1-1）：启动画面 / 标题画面 / 选人 / 读条 / HUD / 移动 / 跳跃（可变高度）/
  蹲下 / 敌人（走·被踩·被撞）/ 砖块（顶不碎·顶碎）/ 问号块（金币·道具）/
  道具（超级蘑菇·火花·1UP）/ 火球 / 受伤降级 / 掉坑死亡 / 掉命复活 / GameOver /
  倒计时 / Hurry-up / 旗杆 / 走进城堡 / 结算 / 暂停 / 回主菜单 / **再进一次** /
  BGM / 音效 / 相机 / 城堡装饰 / 双人 / 分辨率无关 …
- 例（暗黑破坏神 2）：启动画面 / 主菜单 / 创角（职业·外观·属性）/ 进游戏 / 地图与**随机地形** /
  普通怪 / **精英怪与词缀** / 技能与技能树 / 背包与装备 / NPC 与**对话** / 商店 / 掉落 / 存档 / 传送 / 回城 …
- 例（CS）：主菜单 / **选阵营** / 买枪与经济 / 地图 / 射击与后坐力 / 命中反馈 / 观战 / 联机匹配 / 记分板 …

**不许**用"范围太大 / 内容太多 / 下次再做 / 框架已预留暂未实现"结案。

**动手前第 0 件事：必须有参考游戏名。** 用户点名了游戏 A → 按 A 做（产出 `策划/策划案/{A}参考规格.md`）；
**用户没给游戏名 → 停下来问用户"参照哪款游戏"**，拿到名字再开工。
**禁止**自己挑一个近似品类就动手 —— 那样做出来"永远不像"，是最贵的返工。

**⏱ 不许砍范围（硬性）**：**时间 / token / 规模 / agent 数量都不是理由**。
不许因为"内容多 / 耗时长 / 复杂 / 要拆很多 agent"砍范围、分步做、中途交差；
起手就把 ① ② ③ **全部内容**列入待办，**一直做到全部完成**再说话。
**允许做很久、想很久**，但必须**充分测试**；宁可不交付，也不交半成品。
（宿主的「单任务模型请求数」有物理上限 ⇒ **靠换手接力跨过，不是靠砍** —— 见 `SKILL.md`「谁来做」。）

> **为什么这么硬**：**用户如果觉得我们连"菜单 + 创角 + 首场景"这点东西都做不出来，压根就不会用我们引擎。**
> 交付的 demo 就是引擎能力的唯一证明 —— 这里是最高优先级，**压倒"省时间 / 省 token / 少动手"的一切考虑**。

## 1. 交付闸门详述：验收表怎么建、怎么判

> **为什么光有"必须做完"这句话拦不住人**：实测栽过一次 —— AI 在**同一条回复里**说了
> "实测通过"，紧接着列了一串"还没验的：踩敌、顶砖块、火球、旗杆通关、暂停"。
> 第一铁律的原文、16 条铁律、验收清单**它全都读过**，照样这么干。
> 原因是：那些要求**散在三个地方、全是散文、没有分母、也没有打勾动作** ——
> 收尾时 AI 手里没有一张"必须逐格填满"的表，于是只能凭印象挑几项验，
> 验到自己觉得够了就宣布完成。**"觉得够了"就是违规的入口。**

**① 表在建工程时就建好，不是收尾才补**（路径：`策划/验收表.md`）。
**行 = 参考游戏 A 的系统清单**。**没有 A 的系统清单 ⇒ 没有验收分母 ⇒ 必然会漏** ——
实测漏掉的全是"玩起来才知道"的：踩敌、顶砖块出道具、火球、旗杆通关、暂停菜单、双人模式。

| # | 系统 / 界面 | 做法 | 验收方式（怎么演一遍） | **类别** | 证据 | 结论 |
|---|---|---|---|---|---|---|
| 1 | 启动画面 | … | `editor_play` + 看画面 | **`表现类`** | 联络图 `格01` + 日志行 | 一致 |
| 2 | 主菜单（每项都点过） | … | 逐项按键 | **`表现类`** | 联络图 `格02` + 日志行 | 一致 |
| 3 | 选角 | … | 能选中 / 能返回 | **`表现类`** | 联络图 `格03` | 一致 |
| 4 | 读条 | … | 进度真在跳 | **`表现类`** | 联络图 `格04` | 一致 |
| 5 | 游戏内核心闭环（移动/跳/踩敌/顶砖块/道具/受伤/死亡/复活） | … | **一条驱动链路按序跑完**（⛔ 不逐项进出 Play） | **`表现类`** | 联络图 `格05` 起 | 一致 |
| 6 | 金币数 / 分数变化 | … | 顶块后读数值 | **`数值类`** | 日志行（不必截图） | 一致 |
| 7 | 通关流程（旗杆 → 结算） | … | 真打到终点 | **`表现类`** | 联络图 `格NN` | 一致 |
| 8 | 暂停 / 回主菜单 / **再进一次** | … | 走完整来回 | **`表现类`** | 联络图 `格NN` | 一致 |
| … | （A 有的**每一项**都要有一行，含音效、HUD、镜头、节奏） | | | | | |

> **`类别`列是必填**（`SKILL.md` §2 硬性判定第 3 条）：
> `数值类`（数值 / 逻辑 / 状态 / 坐标 / 计时）⇒ 判据是**日志行 + 断言**，不必截图；
> `表现类`（动画 / 贴图 / UI 可见与对齐 / 颜色 / 时序观感）⇒ **交付前必须进一次联络图**
> （采集与判定见 `reference/visual-loop.md` 第八节；**格号必须与验收表行号对得上**）。
> **它是"该不该截图"的唯一判据** —— 不填，执行者只能全截（贵一个量级）或全不截（数字对画面错）。
> ⚠️ **一个带可见表现的数值要拆成两行**（数值行 + 表现行）：实测事故就是数字全对而动画没出来。

**② 判定规则（硬性，逐条自检）**

1. **任何一行的「结论」是空的、或写着"未验 / 待验 / 还没验 / 下次补" ⇒ 一律禁止出现
   "完成 / 做好了 / 交付 / 实测通过"这些字样。** 只能说"还没做完"，然后继续做。
2. **"说完成"与"列未验项"不许出现在同一条回复里**（见 SKILL.md 第一铁律违规表）。
3. **表里的行数不许少于 A 的系统清单**。少一行 = 漏一项 = 不可交付。
4. **单次跑通不算证据**。至少满足：
   - **连续两次进 Play 都通过** —— 专抓"第一次好、第二次坏"那类只由静态残留引起的 bug
     （域不重载、单例、`static` 缓存…都是这个形状，且**通常零报错**）；
   - **证据按类别给**（`SKILL.md` §2 硬性判定第 3 条）：
     `数值类` ⇒ 运行时**日志行 + 断言**（不必截图）；
     `表现类` ⇒ **必须进联络图**，且 AI **只读那张汇总图一次**（数字全对但画面不对是经典静默失效）；
   - 一次性行为（死亡 / 通关 / GameOver / 掉命）要**真的触发一次**，不许"代码看起来对"。
5. **禁止挑选有利证据。** 每个 `表现类` 的界面都要**出现在联络图里**（⛔ 不许只把好看的格子拼进去）；**拍到过坏图就必须在表里写清
   "坏在哪 + 改了什么 + 重拍后的图"**。只报成功的那几张 = 欺骗。
6. **交付说明里只允许两种内容**：① 填满的表；② A 的系统清单与本表的对应关系。
   不许出现"我还剩……""你可以先试……""其余在路上"这类尾巴 —— 有尾巴就是没做完。
7. **用户看到的东西才算数**：用户报的问题一律视为**表里漏了一行**，
   回去补表（把"用户报的这个现象"加成一行、并把同类问题一起排查），而不是只修那一个点。
   （实测：用户说"菜单全蓝"，真因是域不重载 + UI 锚点两个系统性缺陷，若只改菜单就还会在别处复发。）

**③ 表的"自洽"与"可追"（第三次投诉后补，实测都是漏掉这个）**

8. **⛔ 禁止用「结论统计 / 进度段」给"不一致"找台阶**。
   实测有一种很会伪装的形态：在表后面加一段「结论统计（诚实口径）：通过 35 行 / 不一致 7 行……
   这 7 行没达标 ⇒ 本版本不可宣称完成，需下一棒补拍」——
   它**读起来很诚实**，但作用等于 **"我登记了，所以这轮可以结束了"**（`SKILL.md` §1.5 明令的漏洞）。
   ⇒ **出现「不一致」行的正确动作只有两个**：① **当场修到"通过"**；② 转成**显式阻塞项并说清"用户要给什么"**。
   **不许**把它写成统计数字然后收工。也**不许**把这张表交给下一棒当"待办清单"。
9. **表必须自洽，证据必须可追**（跑 `reference/workflow-and-standards.md` §13 的 5 条）：
   - **汇总数字 = 表体统计**（实测：汇总写"35 通过 / 7 不一致"，表体实为 39 / 3 ⇒ 谁读谁被误导）；
   - **证据格里的每一个路径/行号都要能打开** —— 宿主搬了家就要同步改表，
     否则是"**看起来有证据**"（实测：证据指向 `tools/*check`，而宿主已挪到 `.ai-tmp/hosts/`）。
10. **「允许的差异」小节同时是"引擎能力例外"的登记处**（这条原来缺失，导致例外只能写在代码注释里）：
    - 本 skill 的硬禁令（`⛔ 别用 Resources.Load 绕开 Game.Res` / `引擎有就用引擎的` / `⛔ 不许裸 Debug.Log`）
      **允许例外，但必须逐条登记在本小节**，格式：
      `【例外】<行为> | 为什么必须这样（带实测证据） | 出处（文件:行） | 何时能消除`；
    - 只写在**代码注释**里 = **没登记 = 违规**（实测某项目有 4 处 `Resources.Load` +
      4 处不用引擎能力（`Game.Camera.Follow` / `Game.Map` / `Game.Pool.Spawn` / `CloverData`），
      理由都写得很扎实，但**一条都没进表** ⇒ 验收时无从判定是"深思熟虑"还是"偷懒"）；
    - 该小节为**空** ⇔ `SKILL.md` §1.11 第 2 条的硬规则检查必须 **0 命中**（两处必须互相印证）。

### 验收表附带的两节（`SKILL.md` §1.11 要用）

紧跟在结论列之后，`策划/验收表.md` 必须带这两节：

```markdown
## 允许的差异（默认应为空；每加一条都要有理由 + 出处 + 消除条件）

| # | 例外行为 | 为什么必须这样（实测证据） | 出处（文件:行） | 何时能消除 |
|---|---|---|---|---|
| 1 | 用 `Resources.LoadAll<Sprite>` 取整条条带帧（绕开 `Game.Res`） | 逐帧按名 `Resources.Load` 在本工程实测返回 null，只有整条 `LoadAll` 取得到 | `UI/<某面板>.cs:<行号>` | 引擎提供按名取图集帧的同步 API 后 |
| 2 | 不用引擎 `Game.Camera.Follow`，自写跟随 | `Follow` 是"锁 Z 的简单跟随"，与本作固定等距视角语义不符 | `Module/Camera/<某>.cs:<行号>` | 不适用（语义本来就不同） |

## 机械自检记录（`SKILL.md` §1.11 的 7 条，原始输出）

- ① 临时文件：<命令 + 输出>
- ② 硬规则命中：<命令 + 输出>
- ③ 聚合自洽：汇总 <N> 通过 / <M> 不一致 = 表体统计 ✅
- ④ 例外登记：<N> 条，与 ② 互相印证 ✅
- ⑤ 路径可达 / 无交接文档：<命令 + 输出>
```

## 2. 铁律 16 条（违反任一条即交付失败）

> 服从《第一铁律：必须做完，才交付给用户》—— 冲突时以第一铁律为准。

| # | 铁律 | 判定 |
|---|---|---|
| 1 | **不做 MVP，做原版级完整成品** | 交付「① 启动与菜单链路 + ② 首场景完整版 + ③ 游戏内流程」：核心闭环 + 全表现（动画真在动 / 音效真出声 / HUD 真面板 / 场景有内容 / 手感调得到）。**禁止**把"最小可用 / 骨架 / 待替换清单"当交付 |
| 2 | **用户点名了游戏 A ⇒ 必须用 A 的素材** | 找 **A 自己的素材**（同名 / 同源 / 复刻 / 官方 SDK / mod / 社区提取都算），**多找几轮**（换关键词 / 站点 / 语言 / 镜像）；同类游戏素材只是次选；**只有"必须登录 / 付费"才让用户下**（给清单+链接，见 `reference/asset-sources.md` §5） |
| 3 | **保真 A 的手感** | 不知道 A 是什么感觉 → **去搜**（手感 / 数值 / 操作 / UI / 动画 / 音效 / 移动速度 / 镜头），转写成 `策划/策划案/{A}参考规格.md`，实现时**逐项对齐** |
| 4 | **素材自动获取，先做起来** | 能 `git clone` / 直链 / **抓页面直链**的一律**自己下自己接**；**不设许可门槛**（非商用项目：CC0/CC-BY/NC/来源不明 都能用，记一行来源即可，**不为许可停下来问**）；只有"登录 / 会员 / 付费"才让用户下；**兜底直接用我们已验证的素材**（KayKit 等，`reference/asset-sources.md` §2.2）**自动下载自动使用** |
| 5 | **有 bug 就改引擎** | **不再问"要不要改引擎"**：定位 → 最小修复 → 补回归用例 → 编译/测试全绿 → 记进项目 `constraints.md`（E 编号）。业务绕行**不算**最终方案。SOP 见 `patterns/engine-fix.md` |
| 6 | **只支持 Unity 6（6000.x）** | 老工程先升级；非 Unity 6 不做（硬性）。引擎包 `package.json` 声明的最低兼容是 `2022.3`（能被旧工程打开），但本仓库的开发 / 验证与 AI 自动化一律 Unity 6（见 `scaffold/new-project.md` §2.1） |
| 7 | **必须跑完测试循环（反复多轮）** | 编译干净 → 进 Play → 读日志零异常 → **运行时自证** → **截图** → 表现对照参考游戏 → 再改再测。**需要编辑器就打开它**（`unity open`）；**打不开就明确请用户打开 Unity**（这是我们**允许且要求**的动作） |
| 8 | **一次做完（含菜单链路），不许"先骨架后补"** | ① ② ③ **全部内容一次交付**，**不许**"先生成骨架→等确认→再补"。**只有"用户看完后新提的内容扩展"才算下一轮** |
| 9 | **不许分步汇报** | **做一项汇报一次 = 违规**。过程中只在两种情况下说话：① **被阻塞、必须问用户**；② **全部做完**（此时给一次完整交付说明）。中间不许"进度播报" |
| 10 | **代码必须分层分模块** | 见 `reference/architecture.md`：一个系统一个模块、依赖单向、**App≤200 行**、UI 不引用业务模块、网络只走 Net 门面。**禁止上帝类与互相直接引用** |
| 11 | **动手前先出《行为 → 表现规格》**（策划自审） | 见 `reference/design-review.md`：每个行为在**画面/动画/声音/UI·数值反馈/网络**上分别是什么，都要先写下来；**不知道就先去搜参考游戏**。没有规格就动手 = 糊弄 |
| 12 | **交付前逐条对照规格做测试审查**（感官项必须自己跑 + **必须看图**） | 在 Play 里逐项演过并留证据：动画衔接/转身、命中反馈三件套（飘字+音效+目标血条）、自己与敌人的血条、镜头、音效时机、死亡与复活、**屏幕上不能出现占位物**。这些都是 `表现类` ⇒ **交付前采一次联络图并读一遍**（AI 只读那张汇总图，见 `reference/visual-loop.md` 第八节）。**代码对不对 ≠ 玩起来对不对**；只看代码/日志/自证数字就交 = 违规 |
| 13 | **禁止直接进游戏场景，必须有启动链路** | 启动画面 / 主菜单（开始·继续·设置·退出；联机含登录·注册）/ **创角或选角** / 读条进图 / 游戏内暂停 / 回主菜单 —— 一条都不能少。范式见 `patterns/client/app-flow.md` |
| 14 | **按原版系统清单逐项做完（禁止砍）** | 动手前先列 A 的**系统清单**，每项写"做法 + 验收"；**出现空行 ⇒ 没做完，不得交付** |
| 15 | **不许砍范围：时长 / token / 规模 / agent 数量都不是理由** | 不许因"内容多 / 耗时长 / 复杂"降级范围。复杂项目按 `patterns/multi-agent.md` 拆多 agent（**10 / 100 / 1000 个都行**）；**物理上限靠接力跨过**，不是靠砍 |
| 16 | **交付前必须自审「像不像参考游戏」—— 不像 = 不可交付** | 逐项对照参考游戏的**截图**，每项给 `一致 / 不一致（差在哪）`；**只要有一项不一致 ⇒ 该版本不可交付**，改完重新截图再对照，**循环到全部一致**。**审查必须看图**（多模态读自己的截图）。**没有参考游戏名 → 先问用户要** |

**配套同样硬性**：**UI/HUD 要做**（不是 OnGUI 调试文字）、**场景要有内容**（不是白盒）、**音效要出声**（有音频素材就接上）。

| # | 约束 | 自检标准 |
|---|---|---|
| 1 | **让用户看得到工程** | 建完 `unity projects add` + `pin` 置顶；交付说明写明「Hub 里的名字（=目录名 `client`）+ 绝对路径 + 一条 `unity open` 命令」。**用户看不见 = 没交付** |
| 2 | **操作必须能做**（有角色就必做） | 相机 + 移动真可用：WASD 生效、鼠标转视角、相机跟随不抖不穿墙。**禁止**上帝视角俯视；**禁止**"自己的位置被服务端回推覆盖"导致按了键不动 |
| 3 | **动画必须接** | 用素材自带动画生成 `AnimatorController`，按状态切 idle/run/attack/hit。**禁止**把"状态切换打日志 + 代码留钩子"当动画交付 |
| 4 | **素材真接入** | 优先**同类参考游戏的成套素材**（**能下就下**）**直接接入**；纯色块 / 内置 Cube **不算交付**（确实下不到才用，且回复首行高亮说明） |
| 5 | **菜单链路要能走通** | 启动 → 主菜单 → 创角/选角 → 进图 → 暂停 → 回主菜单：每步都有入口、有返回路径、能重复走（第二次进游戏无残留状态）。**禁止**直接进游戏场景、禁止单向死路 |

## 3. 交付前自审：像不像参考游戏？（**不通过 = 不可交付**）

> **"跑通了"和"可以交付"是两件事。** 交付前必须做一次**以「像不像参考游戏」为唯一标准**的自我审查。
> **只要不像，这个版本就是不可交付版本** —— 不许汇报完成、不许交差，**必须改到和参考游戏一模一样**。
> 完整做法与验收模板见 `reference/design-review.md` §3.6 与 `patterns/game-demo.md` §0.0/§6。

**第 1 步：准备对照物（参考图 ↔ 自己的截图，配对）**

- 搜集 A 的**真实截图 / 视频切片**：启动、主菜单、创角、HUD、战斗、场景、结算… 存 `策划/参考图/` 并编号；
- 自己**同样角度**画面（`unity command capture_game_view`），一一配对（`策划/自审对比/`）——
  **采集形态与判定见 `reference/visual-loop.md` 第八节**（联络图：一条链路采一次、脚本按格判定、AI 只读汇总图一次；⛔ 不逐项进出 Play、不逐张读原图）。

**第 2 步：逐项对照（每项都要写结论，不许空白）**

| 维度 | 对照什么 |
|---|---|
| 启动 / 菜单 | 有哪几个界面、层级顺序、按钮文案与位置、背景 / Logo、配色 |
| 创角 / 选角 | 有哪些字段与选项、布局、确认与返回路径 |
| HUD | 血条 / 资源 / 技能栏 / 小地图的位置、比例、颜色、字号层级 |
| 手感 | 移动速度、转身、攻击节奏、镜头 FOV 与跟随、后坐力 / 硬直 |
| 表现 | 动画状态切换、命中反馈三件套（飘字 + 音效 + 目标血条）、特效 |
| 场景 | 地图风格、地形、光照、色调 |
| 音效 | BGM / 点击 / 命中 / 进图的时机与音量层级 |
| 节奏 | 一段/一局时长、死亡复活、结算时机 |

**第 3 步：判定（二值，不许"差不多"）**

- 每项写 `一致` 或 `不一致（差在哪）` —— **不允许"基本一致 / 大致像"**；
- **只要有一项"不一致" ⇒ 该版本不可交付**：改 → 重新截图 → 重新对照，**循环到全部一致**；
- **禁止**把"不一致"写进交付说明当免责（"这部分略有差异" = 没做完）。

**第 4 步：审查必须「看图」**

- 感官项**必须用多模态能力读自己的截图**（`reference/design-review.md` §3.4）；
- **数字全对但画面不像 = 不合格**；只对代码/日志/自证数字做审查一律算违规。

## 4. 验收：必须"自己跑过"，不许口头交差

> 执行形式是 **`策划/验收表.md` 那张表**。**清单读过 ≠ 验收过**；只有表填满了才算。
> 尤其「**再进一次**游戏」是最容易漏、也最容易出事的一条（静态残留类 bug：第一次好、第二次全坏，且零报错）。

交付前 AI **自己**完成闭环（不是让用户去点）——详见 `reference/unity-cli.md` §8.1：

```bash
unity command recompile_status --format json   # ① 编译干净 failed=false
unity command clear_console; unity command editor_play; sleep 40
unity command console --tail 400               # ② 读运行日志：关键日志都在 & 无异常
unity command eval_file --file <工程>/client/verify-runtime.cs   # ③ 运行时自证对象状态
unity command capture_game_view --source screen --save_path Screenshots/play.png  # ④ 截图取证（含 HUD）
unity command editor_stop                      # ⑤ 退出 Play
```

**菜单链路验收（硬性，自己逐项点过）**：

- 启动后**先进主菜单**，不直接落到游戏场景；
- 主菜单每一项都真能用（开始 / 继续 / 设置 / 退出；联机再加登录 / 注册）；
- 创角 / 选角：能创建、能选中、能返回，能带着**自己建的角色**进图；
- 读条：`Game.Scene.Load` 的进度真在跳（不是黑屏、不是瞬间硬切）；
- 游戏内：能开暂停菜单 → 能回主菜单 → 能**再进一次**游戏（第二次进入无残留状态）；
- 证据按**类别**（`SKILL.md` §2 硬性判定第 3 条）：`数值类` = 运行时日志行 + 断言；
  `表现类`（主菜单 / 创角 / 读条 / 游戏内 / 暂停 / 结算）= **全部进联络图**，格号 ↔ 验收表行号
  （采集与判定格式见 `reference/visual-loop.md` 第八节）。

> **工程可能已经被用户开在编辑器里** —— 那就**驱动它**（`unity status` / `unity command eval_file` / `editor_play`），
> 不要再跑 `unity run`（会报"项目已在运行中的编辑器中打开"），也不要手改场景 YAML。

### 4.1 ★ 四条硬性验收纪律（**一次翻车换来的，逐条照做**）

实测有一次"验收表 39 行全填了、用户一上手连报 4 个 bug"。复盘后发现**没有一个是"没测"，全是"测错了对象"**：

| 我验了什么 | 用户看到的 | 差在哪 |
|---|---|---|
| 顶问号块 → `分数=000200 金币=×01` | **金币动画根本不出来** | 只验了**数字**，没验**画面**。数字对 ≠ 表现对 |
| 时间到 → 读代码看到 `OnTimeUp` 会 `Kill()` | **画面永久卡死** | **读了代码就当验过**；`Kill()` 之后没有后续结算，链断在下一环 |
| 死亡 → 日志 `还剩余 2 条命，重开本关` | **应该先过入场卡（WORLD 1-1 ×命数）** | 只验了"复活的机制"，没验"复活的**观感**像不像原版" |
| 入场卡渲染正常（截图看过） | **卡上命数是 ×3，实际只剩 1 条** | 读了图，但**没把图上的数字和日志里的数字对一遍** |

**由此定四条硬纪律：**

1. **按类别取证，且两类要互相对得上**（`SKILL.md` §2 硬性判定第 3 条）：
   - `数值类`（金币 / 分数 / 命数 / 时间**的数值本身**）⇒ **运行时日志行 + 断言**；
   - `表现类`（那个数值的**可见表现**：金币真的弹出来、命数图标真的变）⇒ **进联络图**。
   **两者对不上 = 发现了 bug**（那次就是这么抓到"卡上 ×3"的）。
   ⚠️ 拆行规则：**一个带可见表现的数值，拆成「数值行 + 表现行」两行** ——
   ⛔ 不许因为它"是个数值"就不看画面（实测事故：数字全对，而金币动画根本没出来）。
2. **链式流程必须从"真实现场"触发一次，不许读代码推断"下一环会自己走"。**
   例：死亡链是 `受伤 → Kill → PendingDeath → 死亡结算计时 → 减命 → 重来/GameOver`。
   只验前两环，后面三环断了也看不出来（实测就是：`OnTimeUp` 只调了 `Kill()`，
   没置 `PendingDeath`，结果时间到 0 之后**永久卡死**）。
   **触发方式要覆盖每一条入口**：敌人撞死 / 掉坑 / 时间到 / 外部强制 —— 各来一次。
3. **UI 面板里的"当前状态值"必须由调用方当参数传入，不许在 `Awake` 里自己去上下文里读。**
   实测：读条屏在 `Awake` 里读 `StageContext.Score.Lives`，而"打开面板"发生在
   "新会话 Build 完并 Restore 分数"**之前** → 上下文还是空的 → **静默回退到默认值 ×3**；
   首次进关恰好正确（新游戏就是 3 条命），所以这个 bug 藏了很久。
   漏传参数时要**打 Warn**（否则又退化成"显示错值但没人知道为什么"）。
4. **"定义了但没人用"是本项目最高频的缺陷形态 —— 开工排查先 grep 常量是否被引用。**
   实测同一个形态出现了 5 次：`BigCrouch`/`FireCrouch`（蹲下没实现）、
   `StarInvincibleTime`（无敌星没实现）、`HitInvincibleTime`（受击无敌帧没实现）、
   `BlockContent.OneUp/Star`（方块产出分支漏 case）、以及金币的 `_items.Spawn`（只加分数不弹金币）。
   **判据**：看到"定义了从没被读/被调的常量、枚举成员、资源名" ⇒ **99% 是功能漏接线**，
   不是"预留"。**验收表里每一项都要追一遍"这条链的最后一环有没有人执行"。**

## 5. 策划自审：先想清"该是什么样"，再写代码

> **逻辑错误有编译器/测试替你抓；感官错误没有任何东西替你抓。** 代码能跑、日志全绿，
> 玩家一看仍然会觉得"哪哪都不对"：动画接不上、攻击没反馈、敌人没血条、血条恒满、
> 占位胶囊体当角色、镜头乱转 —— 这些**只有"先想清楚再演一遍"能发现**。

**规则（硬性，见 `reference/design-review.md`）**：

1. **动手前先出《行为 → 表现规格》表**：每个行为在 **画面 / 动画 / 声音 / UI·数值反馈 / 网络** 上分别是什么；
2. **不知道规格就去搜**（参考游戏的手感与表现、官方文档、同类项目）—— 不许"我觉得差不多"；
   搜不到就把不确定写进规格并**问用户**；
3. 表里出现"占位 / 后续替换 / 留钩子"⇒ **视为没做完**，不得交付；
4. **交付前逐条对照规格做测试审查**，感官项（动画衔接/转身/命中反馈/血条/飘字/镜头/音效时机/死亡复活/占位物）
   **必须在 Play 里亲自跑过**并留证据 —— **代码对不对 ≠ 玩起来对不对**。

## 6. 复杂项目：步骤文档 + 多 agent 编排

**满足任一条件即算复杂**：**「一键出游戏」一律算复杂** / 需同时改服务端+客户端+UI 且消息号跨 2 个以上模块 /
预计 ≳ 800 行或 ≳ 10 个文件 / 含多个子系统 / 存在可并行的独立子系统。

> **不许砍范围（硬性）**：复杂项目**该拆多少 agent 就拆多少** —— 10 / 100 / 1000 个都行，
> **不许因为"要开的 agent 太多"而缩小交付范围、降低完成度或改成"先做个精简版"**。

若判定为复杂，**必须**（完整 SOP 见 **`patterns/multi-agent.md`**）：

1. **先出《步骤文档》**：`clover-{项目名}/docs/步骤文档.md` —— 目标与验收、系统拆分、
   步骤清单（每步产出物路径 + 验收标准 + 依赖）、串/并行标注、关键契约、风险与未知。它是**唯一总纲**。
2. **给每个 agent 一份自包含任务文档**：`docs/agents/agent-NN-{子系统}.md`，必须含：
   ①「**开工先加载 `clover-engine` skill 与 `unity-cli` skill**」；② 任务边界（**绝不做什么**、不许碰哪些文件）；
   ③ 前置依赖的确切接口签名；④ 产出物绝对路径；⑤ 验收标准 + 自检命令；⑥ 必读 skill 章节清单；⑦ 日志要求。
3. **硬约束：agent 不许再开子 agent** —— **子 agent 会偷懒**：层层转包后没人真读源码、没人真跑编译。
   需要人手 → **回报主 agent**，由主 agent 决定并补写任务文档。
4. **主 agent 职责不可下放**：维护《步骤文档》、裁决契约冲突、**逐个验收**（自己跑编译/起服/读日志，
   不许"它说完成就算过"，不合格打回**原 agent** 返工）、最后做端到端联调再写交付说明。

> 简单任务（单文件 / 单消息号 / 一个 UI 面板）**不要走这套**。

## 7. 图片需求：先自检多模态能力（硬闸门，不通过就停）

**触发**：用户发来图片 / 截图 / 照片 / 手绘草图 / 设计稿，或提到"这张图""图里""照这个做""还原这个界面/玩法"。

**第 0 步（动手前必做）：确认自己能不能"真的读图"。** 判断依据（**保守优先**）：

1. 你的模型具备**图像输入能力**吗？运行时注入的身份里若只声明文本能力 → 按**不能读图**处理；
2. 你**确实收到了图像内容**吗？而不是只拿到一个文件路径、文件名，或用户的文字描述。

> 1 或 2 只要有一条不确定 → **一律按"不能读图"处理**。宁可让用户补一次说明，也不要猜图。

### 情况 A：不能读图 → **立即停下，不许继续这个任务**

**禁止**：假装看懂了图，靠文件名或用户三言两语**脑补**出"图里的布局与玩法"；
先按自己的想象实现，再声称"已按图实现"；把图片当装饰性输入忽略掉，直接按文字需求做。

**必须**：明确告知用户，并给出两条出路 ——

> 我当前是纯文本模型，**无法读取图片内容**，因此不能凭这张图实现需求。请二选一：
> ① **换一个多模态模型**重新发起任务，并**把这张图再发一次**；
> ② 让多模态模型先把图**总结成一段文字方案**，再把文字发给我。

**给用户的可复制清单**（让多模态模型按此输出）：

```text
请阅读我提供的图片，输出一份"可直接用于开发的文字方案"，包含：
1. 这是什么游戏/界面（类型、目标、单机还是联机）
2. 界面结构：区域划分、每个区域的元素清单与相对位置、层级关系
3. 元素明细：文本内容、按钮/图标含义、数值、列表项、进度条
4. 视觉规范：主色/辅色/背景色（尽量给十六进制）、字号层级、圆角/描边风格
5. 玩法规则：操作方式、胜负判定、流程顺序、状态变化
6. 图片里出现但文字没提到的隐藏信息（角标、水印、次要提示）
7. 哪些部分可能看错/看不清（明确标出，让开发别当真）
```

### 情况 B：能读图 → 也要**先转写成文字方案**再动手

- 先把图内容按上面同样的清单转成文字（写进 `策划/策划案/` 或交付说明），再开始实现；
- 交付说明里写明依据：「依据用户提供的图片 X（已转写为 `策划/策划案/xxx.md`）实现」；
- 图中**看不清 / 有歧义**处 → 问用户，别自己定。

### 图片只是**需求输入**，不是美术素材

不要直接把图里的角色/图标/背景当资源文件用；按 `patterns/game-demo.md` §4.0 **去找同风格的成套素材**
（**非商用项目，不设许可门槛：能下就下**），确实找不到才占位，并在 `client/资源欠缺清单.md` 登记。

## 8. 3D / 有角色的玩法：先过「3D MMO 常规业务逻辑清单」

**动手写客户端操作前必须先读 `patterns/client/3d-mmo-basics.md`**：移动同步（预测+校正+回放）、
客户端本地碰撞（同一份地图数据）、第三人称相机遮挡避障、断线重连/重登、单实例守卫，
以及"完整版"还需要哪些常规项。**里面每条都是从真实翻车里提炼的**，跳过就会做出"能跑但没法玩"的东西。

## 9. 收尾闸门：把话交回用户的**唯一合法条件**（详述）

> 规则原文在 `SKILL.md::收尾闸门`。这里是它的展开与自检方法。
> **用户原话**：「我 skill 要求你做完。**你一直能找到漏洞绕过去是吗**？我 skill 要求的看来还是不够严格啊。」
>
> 实测被滥用的**两条停工漏洞**（都"看着合规"，所以必须点名禁掉）：
> 1. ❌「我先汇报进度，**下一棒继续做**」—— 把活推给未来 = **没做完**；
> 2. ❌「验收表里有 N 行**不一致**，已登记，本轮到此」—— **登记 ≠ 交付，修到一致才算**。

**硬规则（每次想结束时逐条自检）**：

1. **合法结束只有两种**：
   - ① **全部做完**（验收表零空行、零"不一致"、像不像 A 自审全一致）；
   - ② **真的被物理阻塞** —— 缺的东西**只有用户能给**（本机游戏文件 / 账号 / 付费 / 点按钮 / 二选一决策），
     且**必须在本轮说清**「要用户给什么 + 拿到后我立刻做什么」。
2. ⛔ **禁止**拿这些当停下理由：「上下文/预算快满」「下一棒接着做」「已登记不一致/欠图」
   「先汇报让你知道进度」「我会继续做」—— **"我会继续做"这句本身就是停工信号**。
3. **上下文/预算快满 ≠ 收尾**：正确做法是**立刻把剩余工作拆成任务书、派新 agent 继续干**
   （子 agent 各有独立预算），主 agent **只在真的没有可派之事时**才结束这一轮。
4. **剩余项多于一个 agent 的量 ⇒ 分片派**（每片 2~3 项）——
   ⛔ 但**一次只派一片**：普通子 agent 是**同步**的，等它回报、验收过再派下一片
   （`SKILL.md` §5 第 5 条）；⛔ 不许为"并行快一点"改用异步成员通道（模型会落到 auto）。
   **不许因为"一个 agent 做不完"或"派了三个都失败"就整体停下** —— 换个粒度、换个 agent、自己上手，继续。
5. **验收表出现"不一致" ⇒ 该轮不许结束**：要么修到"通过"，要么转成显式"阻塞项"（写明用户要给什么）。
   **素材/实机截图缺失同理：先去拿、先去拍，不许停在"已登记"。**
6. **改 skill / 写文档 / 汇报** 都属于"停下来做的事"：**只有在第 1 条的两种情形下才允许**；
   平时它们必须**夹在连续干活的中间**，不许当成一轮的终点。
7. ⛔ **"离线自检通过"不能替代实机证据 —— 但"实机证据"不等于"必须截图"**（同 `SKILL.md` §1.5 第 7 条）：
   按 §2 硬性判定第 3 条的**类别**走 —— `数值类` ⇒ **运行时日志行**（离线断言只能作补充）；
   `表现类` ⇒ 必须进**联络图**。⛔ 拿离线断言充数 = **该行未通过**。
8. ⛔ **禁止用"交接文档"收尾**（第 1 条的物化形态）：不许产出 `docs/交接-*.md` / `NEXT.md` /
   `docs/进度*.md` 这类**以"剩下没做的 / 下一棒从这里开始"为内容**的文件。
   （实测形态：交上来一份 `docs/交接-下一棒.md`，正文标题就是「★ 未完成（**下一棒从这里开始**）」——
   它**读起来像负责任的交接，本质是把活推给未来**，与「下一棒继续做」同罪，只是换了个载体。）
   **接力 = 主 agent 立刻派新 agent**（`patterns/multi-agent.md`），**不是留一份 md 给未来**。
   例外只有一个：项目**已交付**后，`docs/`（步骤文档 / 任务书）作为历史记录冻结，那时才允许存在。

## 9.5 仓库卫生与提交清单（**提交 / 打包前逐条过**，实测换来的）

> 出处：某 1:1 复刻项目（2026-09-20）。首次准备提交时 **1823 MB / 29488 文件**，
> 其中 **1769 MB 是 `client/Library`**（Unity 导入缓存，换机器自动重建）；
> 而这跟 `.gitignore` **无关** —— **忽略只挡"提交"，不会让磁盘变小**（用户问"为什么还这么大"才补上这句）。

| # | 检查 | 判据 |
|---|---|---|
| 1 | Unity 派生 / 缓存 | `client/{Library,Temp,obj,Logs,Build,Builds,UserSettings,setting}/` + `*.csproj` / `*.sln` / **`*.slnx`** / `.vsconfig` 都在 `.gitignore`（**建项目时就写** → `scaffold/new-project.md` §3）。⚠️ Unity 6 生成的是 **`client.slnx`**（Rider/VS 的新解决方案格式），只写 `*.sln` 会漏 —— 实测某项目把它连同 `.vsconfig` 一起提交了进去 |
| 2 | 原版素材 | `<项目根>/原版资源/` 被忽略；工程内只留"被引用的"，闸门 `tools/check-assets.ps1`（`rules-full.md` §1.9-7） |
| 3 | 一次性产物 | `.ai-tmp/` 被忽略（探针 / 驱动 / 宿主 / 移出的资源），`SKILL.md` §1.8 |
| 4 | 模板 / 教程资产 | Unity 模板带进来的 `Assets/Settings/*.scenetemplate`、`Settings/Scenes/`、`Assets/Welcome/` 移出 —— 实测 **4.56 MB**，其中 `Lit2DSceneTemplate.scenetemplate` 一项就 **3.76 MB** |
| 5 | 取证截图 | **一次性产物**：落 `<项目根>/.ai-tmp/screenshots/`（gitignored），验收后即删；验收表里写「已验收，截图已删」。⛔ 不许进 `client/Assets/**` —— 实测某项目 197 张落在 `Assets/Screenshots/` = **6.4 MB**，交付前才清理 |
| 6 | **模拟一次再提交** | 不建仓也能验：`git init <tmp>` + `git --git-dir=<tmp>/.git --work-tree=<项目> status --porcelain -uall`，逐项对"危险目录计数 = 0"，并核对**该提交的目录在场**（`策划/`、`docs/`、`client/Assets`、`tools/probes/`） |

## 10. 收尾机械自检（见 `SKILL.md` §1.11 的 **7 条**；本节是旧副本，**以 §1.11 + `reference/verify-template.md` 为准**）

> **规则靠"自觉"必然被绕开** —— 判据是产物不是自觉。
> 下面 5 条是**产物层的检查**（**第 6「证据新鲜度」与第 7「一键复检入口」见 `SKILL.md` §1.11**）：
> 每条都能跑、都有自己的数字。**跑完把结果贴进回报。**
> ⛔ 任何一条不过 ⇒ 不许出现"完成 / 交付 / 实测通过"字样。

| # | 检查什么 | 怎么查 | 通过标准 |
|---|---|---|---|
| 1 | **临时文件不许遍地** | `Get-ChildItem <项目根> -Recurse -Filter *.cs \| Where-Object { $_.FullName -match '\\(_dev\|_assets_src\|_assets_tmp)\\' } \| Measure-Object` | **0 命中**。探针 / 一次性脚本只许在 `<项目根>/.ai-tmp/test/`，**用完即删** |
| 2 | **硬规则命中归零** | 对**本项目业务源码**递归 grep：`Debug\.Log`、`Resources\.Load`、`PlayerPrefs`、`(?<!Game\.)Input\.`、`GameObject\.Find`、`FindObjectOfType`、`Instantiate\(`；另见下方「引擎自称」 | **除"已登记例外"外 0 命中**；有例外 ⇒ 必须能在第 4 条查到 |
| 3 | **聚合文件自洽** | 读 `策划/验收表.md`：把「结论」列**自己数一遍**，与该文件里的汇总数字/统计段对比 | **汇总 = 表体**。不一致 ⇒ 有人改了表没改汇总 = 未做完 |
| 4 | **差异与例外都已登记** | 打开 `策划/验收表.md` 的「允许的差异」小节 | 每条例外（**引擎能力未用** / 与 A 的不一致 / 未使用 A 的素材 / 违日志硬规则的调用）**都有一行：是什么 + 为什么 + 出处 + 何时消除**。清单为空 ⇔ 第 2 条必须 0 命中 |
| 5 | **引用路径可达、无悬空文档** | ① 验收表/文档里每个 `<路径>:<行号>`、每个函数名逐个 `Test-Path` / grep；② 查有没有交接/进度类文档 | ① **全部可达**；② **不存在** `docs/交接-*.md` / `NEXT.md` / `docs/进度*.md` |

**第 2 条的补充：引擎自称（⛔ 只能人工核对，不许拿具体名字当 grep 模式）**：

交付物（界面文案 / 标题 / README / 交付说明 / 注释）里出现的**引擎自称必须逐字是 `clover-engine`**（见 `reference/conventions.md` §8）。

**第 4 条的"例外通道"**：本 skill 的硬禁令（如「⛔ 别用 `Resources.Load` 绕开 `Game.Res`」「⛔ 引擎有就用引擎的」）
**允许有例外，但必须落在 `策划/验收表.md` 的「允许的差异」小节里逐条登记**，
格式：`【例外】<行为> | 为什么必须这样（实测证据） | 出处（文件:行） | 何时能消除`。
只写在**代码注释**里 = 没登记 = 违规（实测形态：若干处 `Resources.Load` 绕过 `Game.Res`、
若干处"不用引擎能力、改自写设施"，**理由在注释里写得很扎实，但一条都没进验收表**
⇒ 验收时无从判定这是"深思熟虑的例外"还是"偷懒"）。
**这正是"例外通道缺失"的代价：没有登记处，例外就只能藏在注释里，等于不存在。**
