# Clover 全栈开发 Skill

沉淀 `clover-server-engine/` 与 `clover-client-unity-engine/` 的代码范式，固化团队约定。

> **⚠️ 两份副本，改一处必须同步另一处**：仓库源 `ai-skill/` 与安装副本
> **各宿主的 skill 安装目录各不相同**（一般在用户主目录下 `<宿主>/skills/ai-skill/`）—— 按你实际用的宿主自己定位。
> 两者是**独立目录、不是软链**；只改一处 = 另一处仍是旧版。
>
> **⚠️ 本文件 = 规则层；`reference/`、`patterns/`、`experience/`、`scaffold/` = 能力层。**
> **能力层不许当规则用，也不许拿它当"可以汇报/可以收工"的理由** —— 用到时按需去查，不要一次读完。
>
> **⚠️ 遇到"指针指向空目标"时：报告缺规则，⛔ 不许自己补**
> 文档里出现「详见 §X」「见 `某文件.md` §Y」，而那个节/文件**根本不存在** ⇒
> 这是**缺规则的信号**：正确动作是**报给用户要规则**，⛔ **不许**照着自己对"合理内容"的想象把那一节补出来。
> 实测教训：本文件曾写「落地细节（页签名来源…）见 `patterns/table.md` §xlsx 产出规范」，而那节并不存在；
> 补写的人凭"页签名应该 = 去掉后缀的逻辑名"填了一节 —— **全错**（工具源码里页签名是 `skill_cs`，**后缀保留**；
> 照补出来的写法填，整张表会被打表工具**静默跳过**）。
>
> **涉及工具 / 引擎 / 平台的行为，必须去源码或可复跑的实测输出里查**，⛔ **不许从"文档里的一句话"再推断一层**。
> 判据：**"看起来合理"不是出处**；写出处必须是 `文件:行` 或一段可复现的命令与输出。
>
> **⚠️ 写"实测教训"时必须匿名（本 skill 是所有项目共用的，不是某个项目的复盘笔记）**：
> 可以写**做过什么错、代价多大、正确的形状是什么**；
> ⛔ **不许写**具体项目名（`clover-project-xxx`）、该项目专属的路径与宿主名、专属类名/API 名、
> 以及只有那个项目能对上的数字。判据一句话：
> **读到这段的人，应该能把它套到自己的项目上，而不是猜"这是谁家的事"。**
>
> **同一条的两个推论（都实测踩过）**：
> ① **个案不是规则** —— 不许把某一次的具体字符串 / 具体现象当成**通用检查项**
>   （实测反例：把某次凭空编出来的引擎别名写进 grep 清单 —— 自造名无穷，写死抓不到下一次，还会**假阳性**）；
> ② **具体只许出现在"错误示例"里，不许出现在"检查项"里** ——
>   "当时错成了什么样"可以点名；"以后每次都该怎么查"必须是**可泛化的判据**。

## §0 ★★★ 第零铁律（最高优先级）：做游戏 = **1:1 复刻 A**，不许思考、不许发挥

> **用户原话（多感叹号强调）：「让你做一个游戏，就是要 1:1 复刻，不要过多思考，就去 1:1 复刻！！！！！！！」**

**用户说"做一个游戏 <A>"这句话下发时，目标就已经给定且唯一 —— 把 A 一模一样地搬过来。
没有讨论余地：不许思考、不许权衡、不许改进、不许有自己的想法。**

**唯一判据：A 有 ⇒ 做；A 没有 ⇒ 不加。没有第二个判据。**
**用户没给参考游戏名 → 先停下问用户要**（禁止自己挑个品类开工）。

| ❌ 禁止的"思考"（出现即违规） | ✅ 唯一正确动作 |
|---|---|
| 纠结"这个要不要做 / 值不值 / 能不能砍" | **A 有 ⇒ 做**，照抄完事 |
| "换个更好看的颜色 / 字体 / 布局 / 素材" | **照抄 A 的**（丑的、旧的、不合理的也照抄）；素材从哪来见 §4 闸门 3 |
| "手感优化一下 / 数值调平衡点 / UI 现代化 / 这系统太复杂简化下" | **照抄 A 的**：A 的手感与数值就是标准 |
| 先写"我的方案 / 方案对比 / 取舍建议 / 要不要先做这几项"给用户看 | **不许产出方案**：只许有一张表 ——「A 有什么 ⇒ 现在做到哪」 |
| 自称"致敬 / 灵感源自 / 参考 A 改编 / 精简版 / 现代化重制" | **只准说：正在 1:1 复刻 A** |
| 觉得"做不到"就自己换一种做法 | **先搜别人怎么复刻 A**（现成实现 / 拆解 / rip），**照它的做法抄** |

**硬规则**：

1. **照抄 = 正确动作，不是偷懒** —— 素材 / 布局 / 字体 / 字号 / 色调 / 数值 / 关卡结构 / 音效时机 / 动画节奏一律按 A 逐项对齐。
2. **不许用"思考过程"替代劳动** —— 回复与文档里不许出现"分析了之后 / 权衡之下 / 我建议先 / 考虑到……我选择"。
   要写的东西只有一件：**A 的系统清单 + 每项当前状态**。
3. **不许问"要不要做"** —— 参考游戏有的就得做 ⇒ **自己定**；能找用户的只有"只有用户能给的东西"（参考游戏名 / 本机文件 / 手工操作）。
4. **A 的任何细节都不许自行判定"不重要"** —— 事后说"我以为这个无所谓" = 违规（历史上这类全是被漏掉的核心项，见 §2）。
5. **不许中途降标准** —— 1:1 不许在过程中悄悄退化成"像 / 差不多 / 大致"；**"差不多像" = 不像 = 不可交付**。
6. **唯一例外**：用户在**本轮明说**"不必一模一样 / 参考就行" —— 即便如此也要在交付说明首行写明降级原因；**用户没明说 ⇒ 一律 1:1**。

> **怎么判"是否 1:1"**（对照方法 / 允许差异 / 硬性判定）→ **§2「1:1 复刻硬标准」**。
> **为什么"不许思考"**：多想的那些轮从没让结果更好，只换来"又不像了"的返工。**照抄是最短路径。**

### 用户只报了品类（"做个 MMO / 做个塔防 / 做个消消乐"）怎么办

**品类不是参考物，只有"某一款具体游戏"才是。** 没有 A ⇒ 照抄无对象 ⇒ 必须先把品类收敛成**一个具体游戏 A**。

| 情况 | 动作 |
|---|---|
| 用户报了具体游戏 | 直接用，1:1 复刻（§0 全部适用） |
| 用户只报**品类 / 玩法**（做个 MMO、做个塔防、做个吃鸡） | **停下来问一句**（这是"只有用户能给"的东西）：给 **2~3 个该品类标杆候选**（**同品类但不同子类型**，不许都是同一款），让用户挑一个；拿到名字立刻开工 |
| 用户回"你定 / 随便 / 看着办" | **由 AI 选定一个标杆**，把名字与理由写进 `策划/策划案/{A}参考规格.md` 顶部「形态」一节，**然后照 §0 全程 1:1 复刻它**；中途不许换成"我自己的设计" |
| 用户报的是**形态**（MMO / 联机对战 / 单机）而不是玩法 | 形态只决定"要不要服务端"（§4 闸门 0） —— **不能替代参考物**，仍要问出具体游戏 A |

**硬规则**：

- ⛔ **禁止"没参考就自己从 0 设计一个"** —— 无参照 = 必然不像 = 最贵的返工；**参考物只能是一款具体游戏**。
- **只问一次、只问一句**：候选 + 一句话，拿到名字立刻闭嘴开工（不许借"没参考"反复确认）。
- 候选**不许拿"我们自己设计的方案"凑数**；也不许替用户拍板（除非用户明说"你定"）。
- 拿到名字之后的一切同 §0：**1:1 复刻，不许发挥**。
- 例（MMO）：候选 = 传奇类 2.5D 割草 / 魔兽世界类 3D 副本 / 剑网3 类社交 —— 都是**具体游戏**，不是"一个 MMO 该有的样子"。

**用户说"你定"时，AI 自选标杆的**四条依据**（防乱选）：

1. **同品类** —— 在用户报的品类内挑，不许跨品类发挥；
2. **载体可得** —— 必须能拿到**一手载体**（rip / 反汇编 / 关卡数据 / 图集 / 官方 SDK）；拿不到载体 ⇒
   "复刻"根本执行不了。**优先选有社区解包的老游戏**（素材、数据、文档都齐，见 §0.5）；
3. **规模可交付** —— 不选一个大到做不完的（做半截 = §1 违规）；
4. **只告知、不等待** —— 名字与理由写进 `策划/策划案/{A}参考规格.md` 顶部「形态」，
   并**一句话告知**用户"我按 X 做"，然后**立刻开工**（**告知 ≠ 求许可**，不违反 §3）。

### 用户**明说**不做复刻（"做个原创 / 不要抄现成的"）怎么办

> **此时第零铁律被用户本人覆盖**（§1.10：用户本轮明说 > skill 规则层）。
> 但**不等于"没有判据了"** —— 而是**标准答案换了一个来源**：从「参考物」换成「**用户规格书**」。
> ⛔ **不许**借"做原创"四个字自由发挥；**验收强度一点都不能降**。

| 事项 | 怎么做 |
|---|---|
| **唯一标准答案** | **用户规格书**：把用户的口述 / 文字 / 草图落盘成 `策划/策划案/原创规格.md`，**逐条编号**（§1、§2…）；开工前把条款**念回给用户确认一次**（这属于 §3 允许开口的"只有用户能给"） |
| **验收判据** | **每条规格必须带一个可执行判据**（脚本断言 / 数值 / 视觉，三选一）—— **没判据的条款不许进表**（否则又是"差不多"） |
| **`§0.5` 的"出处"** | 出处从「参考物 `文件:偏移`」改成「**规格条款编号**」（如 `规格 §3.2`）。常量 / 坐标 / 数值**指不出条款的，一样不许进工程** —— 要么问用户，要么登记「本项目新增」并**另设**验收标准 |
| **`§0.7③` 基线图** | 换成「**规格图**」：用户给的草图 / 参考图 / 口述**量化成的表**（采集与比对流程同 `reference/visual-loop.md`） |
| **`§0.7④` diff 闭环器** | **保留** —— 只把比对对象从"参考物那一侧"换成"规格图" |
| **`§1.12` 第 4 条**（基准不许来自我们自己的产物） | **仍然成立**：基准 = 规格书（用户给的），⛔ 不是我们自己写的实现说明 |
| **交付说明首行** | 必须写明「**用户明说不做 1:1 复刻 ⇒ 按《原创规格》交付**」（同 §0 硬规则 6 的精神，免得下一棒又拿 1:1 判它） |

## §0.5 ★★★ 复刻 = 解析 + 搬运（**禁写条款**）

> 一句话判据：**这个东西参考物里已经有了吗？有 ⇒ 必须解析出来，不许写。**
> 规则层只留祈使句；案例与教训一律写进 `experience/`。

**1. 参考物里已有的东西，禁止重新实现**

范围：几何与碰撞、模型顶点与骨骼、动画序列与帧率、贴图与字体、界面元素的坐标/尺寸/颜色、
数值与公式（速度、摩擦、重力、后坐力、散布、伤害、冷却、时长）、音频、文本排版。

- **正确**：从**权威载体**解析出来，原样搬运。
- **禁止**：凭理解 / 印象 / 常识**在业务里重做一遍**（"搭一个看起来像的"、"定一个合理的值"）。
- **判据**：**写不出出处的量一律不许进工程**；"看起来合理"不是出处。

**2. 开工第一步：定位并解析权威载体**

| 参考物形态 | 权威载体 | 动作 |
|---|---|---|
| 安装包 / 卡带 / 资源包 | ROM、MPQ / CASC、pak、assets | 解包 → 解析 → 落盘成可读数据 |
| 可执行程序 | 写死在代码里的常量与公式 | 读源码 / 反汇编 / 取常量表 |
| 地图或关卡文件 | 专用格式（BSP、TMX、自研表…） | 解析**原始结构**（笔刷 / 平面 / 网格），**不许栅格化成近似** |
| **只有参考图** | **图片本身** | **量化成表**（x / y / w / h / RGB / 层级）+ 同分辨率逐像素比对 |

**载体由执行者自己去弄到手 —— 不是等用户给**（用户手上通常什么都没有）。
必须穷尽获取途径：**≥4 轮不同关键词（中英各半）× ≥3 类站点 × 换过格式与打包方式**
（判据同 §4 闸门 3）；**"下不动"不算"没有"**（换镜像 / 网盘 / 论坛附件 / rip / 录屏逐帧都试过才算）。

**载体降级链**（逐级往下用，**每降一级都要登记"上一级为什么拿不到"**）：

1. 可解包的原始数据（ROM / 资源包 / 游戏安装文件）
2. 可执行程序里的常量与公式（源码 / 反汇编）
3. 专用格式的原始结构（地图笔刷与平面、关卡字节表）
4. **参考图 / 视频**（截图、wiki、录像逐帧）→ 量化成表 + 同分辨率逐像素比对
5. 以上**全部真拿不到** ⇒ **才**升级为阻塞项，并报清"缺什么 / 谁能给"

⛔ 禁止"一边没载体、一边凭印象写"；也⛔ 禁止把"我没去找"说成"没有载体"。

**3. 只有参考图时的边界（必须写明）**

- 图**能**锚住：静态视觉（界面布局、文字位置、色调、构图、模型比例）。
- 图**锚不住**：手感、动画节奏、交互反馈、音效时机（都是时间序列，图里没有）
  ⇒ 标 `BLOCKED：<缺什么 / 谁能给基线>`，或由人给出基线；⛔ 不许凭印象定。
- 图未覆盖关键状态（菜单 / HUD / 战斗 / 结算）⇒ 报缺，不许补。

**4. 唯一允许"自己设计"的情形**

参考物里**确实不存在**的东西（它没有的功能、自研设施）⇒ 显式标注 **"本项目新增"**，
并用**另一套**可验证标准验收（不与参考物比对）。

> **整项目都没有参考物**（用户明说"做原创"）⇒ 见 §0「用户**明说**不做复刻怎么办」：
> 标准答案换成**用户规格书**，出处换成**条款编号** —— **判据不消失，只换来源**。

## §0.6 ★★★ 必然性规则不许只写在 skill 里（**提示词是请求，闸门才是保证**）

> 出处：*"A system prompt is a request. A hook is a guarantee."*；
> **"提示词合规具有非零失败率，程序化闸门具有零失败率"** —— 详见 `reference/deterministic-gates.md`。

**判定（按"行为种类"分，不按重要性分）**：

| 行为种类 | 手段 |
|---|---|
| **必须始终成立的硬性不变量** | **脚本 / 钩子 / 权限规则（零失败率）** |
| **偏好 · 概率性判断**（风格、约定、倾向、措辞） | 写在本 skill 里即可 |

**硬规则**

1. **本 skill 只装"偏好类"。** 凡是"必须始终成立"的（不许编数值 / 交付必须过闸门 /
   编译失败必须停 / 外观必须与原版对照），**都必须同时存在于脚本或钩子里**；
   **只写在这里 = 非零失败率 = 迟早被绕过。**
2. **三个落点**：① `tools/verify.ps1`（模板见 `reference/verify-template.md`）；
   ② **停止前钩子**：交付前跑闸门，有 FAIL 就**拒绝结束**；
   ③ **会话开始 / 每次提交时注入必读卡**（**只注入那张卡片，别把正文一起灌进去** —— 正文太长，灌了等于没灌）。
3. **为可闸门性设计工具面**：把高风险动作做成**专用、类型化的入口**（如 `tools/verify.ps1`），
   ⛔ 不要藏在自由命令里，否则 harness 拿不到可拦截的钩子。
4. ⛔ **外观验收的检测层绝不许用 AI"看图"**：检测用确定性**像素 diff**（pixelmatch / ODiff，
   基线必须与运行时同环境生成）；**AI 只做分诊（聚类、摘要、滤噪声），终审是人**。
   依据：多模态模型在"找出两张图里缺了什么"这类任务上被实测失败过（见 `reference/deterministic-gates.md`）。

## §0.7 ★★ 1:1 的四个部件（每个游戏项目必备；**缺哪个，就不许进哪个阶段**）

| # | 部件 | 通用 / 项目 | 何时必须就位 | 缺了会怎样 |
|---|---|---|---|---|
| ① | **闸门** `tools/verify.ps1` | **通用模板**（`reference/verify-template.md`）复制即用 | **开工时** | 缺 ⇒ **不许写任何代码** |
| ② | **强制层**：让闸门在"必经点"自动跑（**通用层**：git hook / CI / 打包入口；有钩子的宿主再加钩子） | **通用**（不绑定任何产品；适配表见 `reference/deterministic-gates.md` 第五节） | **开工时** | 缺 ⇒ 闸门只是文字，非零失败率 |
| ③ | **基线图 + 场景清单**（`策划/基线图/`） | **项目数据**（参考物那一侧的截图，每个关键状态≥1 张：菜单/HUD/战斗/结算）；采集流程通用（固定分辨率/冻结动画/固定相机位姿）。**用户明说不做复刻 ⇒ 换成「规格图」**（见 §0「用户**明说**不做复刻怎么办」） | **写第一行外观/UI 代码之前** | 缺 ⇒ 外观没有任何"对不对"的判据 |
| ④ | **diff 闭环器**（三信号比对 → 待办清单 → 喂回执行者 → 迭代到容差内） | **通用引擎**（`reference/visual-loop.md`）；换引擎只换"采集器"适配层；**比对对象可换成规格图** | **写第一行外观/UI 代码之前** | 缺 ⇒ 只能靠"我觉得像"结题 |

**硬规则**

1. ①② 缺 ⇒ 不许写代码；③④ 缺 ⇒ **只许做逻辑/数据，不许碰任何外观/UI**。
2. 四件全齐后，外观验收**只走**「三信号 diff → 待办清单 → 迭代到容差内」，
   ⛔ **不许以"我觉得像 / 肉眼看差不多"结题**（依据：`reference/visual-loop.md`）。
3. 跨引擎的 3D 画面：诚实目标是**容差内**（字节一致需复刻渲染管线）；数据/数值/UI 坐标必须 **diff = 0**。

## §1 ★★★ 第一铁律：必须做完，才交付给用户

> **没做完 = 不许交付。没有例外，没有"先给你看看"，没有"剩下一点下次补"。**
> 交付的判定只有一条：**用户要的东西全部做完了吗？** 答"没有" ⇒ **闭嘴继续做**，不许说"完成了"。

| 违规行为（出现即交付失败） | 正确做法 |
|---|---|
| **做一点交一点**（模块 A 做完就发一版让用户看） | **闷头把全部做完**；中途只允许两种发言：① **被阻塞、必须问用户**；② **全部做完** |
| **交付最小可运行版本 / 骨架 / 半成品** | 交付**原版级完整成品**：该有的系统、表现、手感一个不少 |
| 交付后又补一句"其余部分还在路上 / 你可以先试这个" | **不许把未完成品叫交付**；没做完就只能说"还没做完" |
| **同一条回复里既说"完成 / 做好了 / 实测通过"、又列"还没验的 XXX"** | 这是"做一点交一点"的**同一种违规** —— 把"一点"换成"大部分"并不改变性质。**要么闭嘴做完，要么别用"完成"二字** |
| **问"要不要继续 / 接下来做 X 吗 / 还需要我做什么 / 你看这样行吗"** | ★ **这【不是】"被阻塞"**，是变相的进度播报 + 索取许可，与"做一点交一点"同罪。**把这句话删掉，继续做**（"真被阻塞"的判定标准见 §3） |
| 用"范围太大 / 时间不够 / token 不够"砍范围 | **一律不许砍**（时长 / token / 规模 / agent 数量都不是理由）。**物理上限用「接力」跨过去**，不是用「砍」绕过去 —— 见 §5 |
| **在 A 之外自行发挥 / 自行改设计 / 先写方案给用户看** | **犯了 §0 第零铁律** —— 照抄 A 即可，不许有自己的版本 |

**三条细则**：① 不许做一点交付一点；② 不许做最小可运行版本；③ **必须 1:1 复刻 A（照抄即可 —— §0）**。

## §1.5 ★★★ 收尾闸门：把话交回用户的**唯一合法条件**（第三次投诉后加，**最优先于一切"进度汇报"**）

> **用户原话**：「我 skill 要求你做完。**你一直能找到漏洞绕过去是吗**？我 skill 要求的看来还是不够严格啊。」
>
> 实测被滥用的**两条停工漏洞**（都"看着合规"，所以必须点名禁掉）：
> 1. ❌「我先汇报进度，**下一棒继续做**」—— 把活推给未来 = **没做完**；
> 2. ❌「验收表里有 N 行**不一致**，已登记，本轮到此」—— **登记 ≠ 交付，修到一致才算**。

**硬规则（每次想结束时逐条自检）**：

1. **合法结束只有两种**：
   - ① **全部做完**（验收表零空行、零"不一致"、像不像 A 自审全一致）；
   - ② **真的被物理阻塞** —— 缺的东西**只有用户能给**（本机游戏文件 / 账号 / 付费 / 点按钮 / 二选一决策），
     且**必须在本轮说清**「要用户给什么 + 拿到后我立刻做什么」。
2. ⛔ **禁止**拿这些当停下理由：「上下文/预算快满」「下一棒接着做」「已登记不一致/欠图」
   「先汇报让你知道进度」「我会继续做」—— **"我会继续做"这句本身就是停工信号**。
3. **上下文/预算快满 ≠ 收尾**：正确做法是**立刻把剩余工作拆成任务书、派新 agent 继续干**
   （子 agent 各有独立预算），主 agent **只在真的没有可派之事时**才结束这一轮。
4. **剩余项多于一个 agent 的量 ⇒ 分片派**（每片 2~3 项）——
   ⛔ 但**一次只派一片**：普通子 agent 是**同步**的，等它回报、验收过再派下一片（§5 第 5 条）；
   ⛔ 不许为了"并行快一点"改用异步成员通道（模型会落到 auto，见 §5 第 2 条）。
   **不许因为"一个 agent 做不完"或"派了三个都失败"就整体停下** —— 换个粒度、换个 agent、自己上手，继续。
5. **验收表出现"不一致" ⇒ 该轮不许结束**：要么修到"通过"，要么转成显式"阻塞项"（写明用户要给什么）。
   **素材/实机截图缺失同理：先去拿、先去拍，不许停在"已登记"。**
6. **改 skill / 写文档 / 汇报** 都属于"停下来做的事"：**只有在第 1 条的两种情形下才允许**；
   平时它们必须**夹在连续干活的中间**，不许当成一轮的终点。
7. ⛔ **"离线自检通过"不能替代实机证据 —— 但"实机证据"不等于"必须截图"**：
   按 §2 硬性判定第 3 条的**类别**走 ——
   - `数值类` ⇒ 实机证据 = **运行时日志行**（真跑出来的）；离线断言只能作**补充**；
   - `表现类` ⇒ 必须进**联络图**（交付前采一次）；拿离线断言充数 = **该行未通过**。
   （实测被滥用：有人写了三行「离线自检宿主全 OK」就标通过，**实机从没跑过**。）
   ⛔ 反过来也不许：为了"怕漏"就给每个 `数值类` 行都截一张图 —— 那是把最贵的动作重复几十次。
8. ⛔ **禁止用"交接文档"收尾**（第 1 条的物化形态）：不许产出 `docs/交接-*.md` / `NEXT.md` /
   `docs/进度*.md` 这类**以"剩下没做的 / 下一棒从这里开始"为内容**的文件。
   （实测形态：交上来一份 `docs/交接-下一棒.md`，正文标题就是「★ 未完成（**下一棒从这里开始**）」——
   它**读起来像负责任的交接，本质是把活推给未来**，与「下一棒继续做」同罪，只是换了个载体。）
   **接力 = 主 agent 立刻派新 agent**（`patterns/multi-agent.md`），**不是留一份 md 给未来**。
   例外只有一个：项目**已交付**后，`docs/`（步骤文档 / 任务书）作为历史记录冻结，那时才允许存在。

## §1.6 ★★ 品牌与署名（硬约束，**每个游戏都要有**）

- **引擎名只有一个：`clover-engine`**。
  ⛔ **禁止编造别名 / 花名 / 中译名**。实测教训：AI 凭空把引擎写成「**黑月引擎（Clover）**」放进了
  游戏首页，用户质问「**我们也不叫黑月引擎。我也不知道你首页上的黑月是怎么来的？？？**」。
  ⇒ **任何界面、文档、注释、交付说明里出现非 `clover-engine` 的引擎自称，一律算 bug，立刻铲掉。**
- **所有做出来的游戏，首页页面下方必须有一行署名**：**`by clover-engine`**
  （居底居中、字号小、颜色低调，不抢画面）。它要**写进该游戏的 `策划/验收表.md` 一行并实机截图验证**。
  - **"首页"= 玩家看到的那个首页（标题屏 / 主菜单）**，⛔ 不是"只在启动瞬间闪一下的那个画面"。
    启动画面也有不反对，但**首页那一处是硬要求** —— 两处都要能指到实机截图。
  - **判据是"渲染出来的东西"**：⛔ 只写在代码里不算、grep 到源码字符串**不算** ——
    必须在**实机截图**上看得见，且**逐字**（`by` / 连字符 / **大小写**全都要对）。
  - **实测（两处都是"源码全绿、画面不对"）**：① 署名只挂在了启动画面，**标题屏没有**
    （用户肉眼发现：「首页面没有 skill 要求的 by clover engine 好像」）；
    ② 启动画面那一行的源码文本确实是 `by clover-engine`，但用的是**只有大写的像素字体**
    ⇒ 画面上渲染成 `BY CLOVER-ENGINE` —— **大小写不符同样算不合规**。
    ⇒ 闸门条目 `engine-credit` 的判据必须是**运行时 UI 节点树里那个标签的实际文本 + 实际字体**
    （或字形比对），**⛔ 不许 grep 源码字符串**（见 `reference/verify-template.md` 第 10 条）。
- 顺手清理：**把这次自造出的那个名字**在仓库里全局 grep 一遍，出现的地方一起改掉
  （⛔ 别只改首页那一处）。**每次自造的名字都不一样，按当次实际出现的字符串搜** ——
  上面那个名字只是历史个案，⛔ **不许把它当成固定检查项写进别处**（个案不是规则，且会假阳性）。

## §1.7 ★★ 配表 xlsx 产出规范（硬约束，用户第三次点名）

| 要求 | 说明 |
| --- | --- |
| **文件名用中文** | **一个功能一个 xlsx**，文件名用中文：`战斗.xlsx`、`技能.xlsx`；⛔ **不许** `skill_cs.xlsx` 这种"英文名+后缀代码" |

## §1.8 ★★ 临时测试文件规范（**不许遍地拉屎**）

> **用户原话**：「我发现一个问题，**测试问题遍地都是**，一会 `tools` 里，一会根目录，一会放一个地方。
> 再改 skill，**新增一个 `tmp` 目录，里面放一个 `test` 文件夹，专门做各种测试，用完就删掉测试文件，别遍地拉屎！**」

**硬规则**：

1. **一切"一次性"的东西统一放 `<项目根>/.ai-tmp/test/`（新建目录）**，包括：
   探针脚本、驱动脚本、注入脚本、临时截图、临时日志、验证用的小程序、解包/转换的中间产物。
2. ⛔ **不许**散落在：**项目根**、`tools/`、`client/_dev/`、`Assets/`、`策划/`，
   **以及"工程外"** —— **工作区根** 与 **宿主会话产物目录**（宿主那套"结果展示 / 产物落盘"通道就在那里）。
   （实测违规：探针在 `client/_dev/`、脚本在项目根、验证程序在 `tools/xxxcheck/` 各来一份。）
   **本条已做成闸门条目 `no-escaped-artifacts`（"工程外产物"）**（`reference/verify-template.md` **第 13 项**，含可直接抄的代码）——
   §0.6 的判据：只写在 skill 里 = 非零失败率。实测有人把一次性报告写进**宿主产物目录**，
   **工程内扫描当时全绿，是用户肉眼发现的** ⇒ 该条按第 13 项的三条约束落地，别自己另发明。
3. **用完即删**：该验证做完（或本轮任务结束）就**把 `.ai-tmp/` 里的东西删掉**。
   判定标准一句话：**这东西下一次还会用吗？不会 ⇒ 放 `tmp/test/` 且用完删。**
4. **正式位置只放正式物**：
   | 位置 | 只放什么 |
   | --- | --- |
   | `tools/` | **只放正式工具**：会被**反复长期使用**的资产（素材解码器、打表配置…）。⛔ **不许把测试宿主堆这里** |
   | **`.ai-tmp/hosts/`** | **一切测试/自检程序**（`*check` 宿主、验证小程序、跑测试的脚本）—— **用完删** |
   | `.ai-tmp/screenshots/` | **验收证据图**（验收表里引用到的）—— ⛔ 不是 `Assets/Screenshots/`：取证截图是一次性产物，落 `.ai-tmp/`（跟 `.ai-tmp/` 一起被 gitignore），⛔ 不许进 `client/Assets/**`（本节下文与 §1.8 / `game-delivery.md` §9.5 第 5 条同口径；**此处旧版曾把 `Assets/Screenshots/` 写成合法位置，与规则层冲突，2026-09-20 订正**） |
   | `策划/` | 策划文档、验收表、素材调研 |
   | **`tmp/test/`** | **其它一切一次性的东西**（用完删） |
5. **`.ai-tmp/` 不进交付**：写进 `.gitignore`；交付说明里**不出现 `.ai-tmp/` 路径**。
6. **收尾要清场**：接手/收尾时发现历史遗留的散落测试文件，**一并清掉或归位**；
   验收截图是**一次性产物**：落 `<项目根>/.ai-tmp/screenshots/`（跟 `.ai-tmp/` 一起被 gitignore），
验收表里**不引用图片文件**、对应单元格写「已验收，截图已删」，交付前删掉；`client/Assets/Screenshots/` 若已存在 ⇒
交付前删除并写进 `.gitignore`。
⛔ 不许把取证截图放进 `client/Assets/**`（实测代价：某项目 197 张落在 `Assets/Screenshots/` = 6.4 MB，
交付前才清理，并回头改了验收表 18 处引用）。

## §1.9 ★★ 「原版资源」目录（**所有下载/解包素材的唯一来源**）

> **用户原话**：「如果要**下载的资源**，创建一个新文件夹，就叫 **原版资源**。
> 以后你游戏里使用的资源**从这个文件夹里复制走**！！！！！！！！！」

**硬规则**：

1. **所有"下载 / 解包 / 提取"来的原版素材**（安装包、`.mpq`、解包产物、rip 的 PNG / 模型 / 音效 / 文本 / 字体 / 图标）
   **只放一个地方**：**`<项目根>/原版资源/`**（**名字就叫这四个中文字，不许改名、不许改成英文**）。
   内部按用途分层（例：`原版资源/安装包/`、`原版资源/mpq/`、`原版资源/解包原始/`、`原版资源/导出的png/`），
   ⛔ **不许散到工作区各处**（实测违规：解包产物在 `_assets_src/`、工作区根、项目里各来一份）。
2. **工程里用的素材必须"复制"过去**：**`原版资源/**` → `client/Assets/Resources/**`**。
   ⛔ **不许**让 Unity 工程直接引用/依赖 `原版资源/`（它不是资源目录），⛔ **不许**边解包边原地引用。
3. **复制是唯一搬运方式**：将来换素材 = **改 `原版资源/` 里的源文件 → 重新复制一遍**，**不动业务代码**。
   ⇒ 所以工程内的资源路径必须**收敛**（客户端一律走 `Core/ResPaths.cs` 常量，不许散落字符串）。
4. **`原版资源/` 默认不进 git、不进交付包**（体积大 + 原版版权物）：写进 `.gitignore`。
   **唯一例外（用户本轮明说才生效）**：用户要求"原版素材随交付一起给" ⇒ 按第 9 条打包 + git-lfs 提交。
   但**必须留一份清单** **`原版资源/清单.md`**（来源 URL / 包名 / 解包命令 / 导出了什么 / 复制到工程哪些路径），
   **换台机器照着清单能完整复现**。
5. **旧位置清理**：历史遗留的 `_assets_src/`、工作区根散落的解包产物 ⇒ **一并迁进 `原版资源/` 并删掉旧目录**。
6. **进工程是"按需取用"（pull），不是"整包搬运"**：只复制**被业务代码 / 关卡数据真正引用**的那几个文件；
   ⛔ 不许把整包 / 整张素材表（或它的**全量切片**）灌进 `client/Assets/**`。
   **实测代价（`clover-project-super-mario`，2026-09-20）**：三张原版素材表被整片切片进
   `Assets/Resources/Sprites/**` ⇒ `Resources` 里 953 个资源文件 **795 个无任何引用**
   （Items 95% / Enemies 88% / Tiles 80% / Scenery 72%）；`smb1_misc_sprites_0..548` 全在，
   而 `Core/ResPaths.cs` 只引用其中 **8 个**。体积只有 1.26 MB，但**文件数**翻了几倍，
   "哪个切片对应哪块砖"只能靠人猜 ⇒ 仓库噪音 + 提交体积错觉 + 加素材必然踩错。
7. **这条必须是闸门，不是提醒**（§0.5「必然性规则必须做成闸门」）：项目侧跑
   `tools/check-assets.ps1` —— `client/Assets/Resources/**` 里凡有**未被任何 `.cs` / 关卡数据引用**
   的文件 ⇒ **FAIL**（口径：文件名在 `Scripts/**/*.cs` + `Resources/Levels/*.txt` 全文里 `-notmatch`）。
   只写提醒的规则，实测都会烂回去。
8. **清单要能"精确重建"**：`原版资源/清单.md` 逐条写「源文件 → 工程目标路径」（**含切片矩形 / 帧号 /
   导出命令行**），换台机器照它能把工程内的资源集合**复现成同一份**；⛔ 不许只写"从 X 解包来的"。
9. **交付打包（仅当用户本轮明说"原版素材随交付一起给"）**：`tools/pack-original-assets.ps1`
   → `<项目根>/原版资源.zip` + **git-lfs** 提交（`.gitattributes`：`*.zip filter=lfs diff=lfs merge=lfs -text`）；
   zip **只放仓库根**，⛔ 不许进 `client/Assets/**`；sha256 + 脚本版本记进 `清单.md`。
   细则（命令序列 / 可选裁剪）→ `reference/asset-sources.md` §8.2。

## §1.10 ★★★ 规则层的否决权（**本 skill 的规则层，任何项目文档都不得覆盖**）

> **为什么单列这条（实测，根因在 skill 不在 agent）**：
> 本 skill §1.8 明写「⛔ 不许把探针放 `client/_dev/`」，而**某个项目的 `tools/ai-skill/constraints.md`
> 把探针位置反过来写死成 `client/_dev/`**（好几处）⇒ 最后那个目录堆了**上百个文件**。
> 子 agent **不是不听话** —— 它读到的是**本 skill 自己在几份模板里写的**
> 「项目约定优先 / 优先于通用写法 / 冲突时以本项目为准并说明」，于是它照章选了项目文档，
> **还老老实实在回报里说明了冲突**。⇒ **责任在 skill：把否决权交给了项目文档。**
>
> ⚠️ **本节不针对任何具体项目**：「项目约定优先」这个歧义写法是**全局模板**的锅，
> 已在 `scaffold/**` 与 `patterns/multi-agent.md` 一并修正。实测案例一律匿名，
> **只保留可复用的形状与代价，不保留项目名 / 项目专属路径 / 项目专属类名**。

**层级（越靠上越硬，下面只能加严不能放宽）**：

| 层 | 谁 | 能不能推翻下一层 |
|---|---|---|
| ① 用户本轮明说 | 用户 | — |
| ② **本 skill 的「规则层」（§0~§7，含 §1.x）** | 本 skill | **⛔ 谁都不能推翻**（项目级 skill / 项目文档 / 既有代码 / 别人的工程都不行） |
| ③ 项目级 `<项目根>/tools/ai-skill/` | 项目主 agent | 只能**加严** ②，不许放宽 |
| ④ 项目文档（`docs/`、`策划/`、代码注释） | 任何 agent | 只能加严 ②③，不许放宽 |
| ⑤ 既有代码 | — | **不是依据**（"别人/以前就是这么写的" ≠ 可以这么写） |

**「项目约定优先」的正确含义（模板原文有歧义，一律以本处为准）**：

- 项目约定**只在**「本 skill 没写」或「本 skill 明说可自选」的地方优先 ——
  如技术选型、命名、目录细分、消息号分段、配表字段名。
  （这正是"项目级 skill 存在的最大理由"：历史包袱与特殊取舍，见 `scaffold/project-skill.md` §2。）
- **凡本 skill 标了 `§0~§7` / `⛔` / **硬规则** / **硬约束** / **硬闸门** 的地方，项目约定一律不得冲突。**
- 冲突时的正确动作是**三步，不是"在回报里说明"**：
  1. **照本 skill 规则层做**；
  2. **把冲突的那份项目文档改掉**（模板/约束/步骤文档/注释一起改）；
  3. 若真认为规则层不合理 → **回报用户，由用户决定改 skill**；⛔ **不许自己在本项目里放宽**。

**交付前自检**：对本项目 `tools/ai-skill/` 与 `docs/` grep
`与全局 skill 的差异|以本项目为准|优先于全局|优先于通用` ——
命中处**逐条判**它是**加严**还是**放宽**；**放宽的一律改掉**（改成加严，或删掉那一行）。

> 落地位置：`scaffold/new-project.md`、`scaffold/project-skill.md`、`scaffold/agent-impl.md`、
> `patterns/multi-agent.md` 里的"项目优先"表述**已按本节的正确含义修正**。

## §1.11 ★★ 收尾机械自检（**8 条，可复制执行；全过才允许说"完成"**）

> **规则靠"自觉"必然被绕开** —— §1.5 已说过「判据是产物不是自觉」。
> 下面 **8 条**是**产物层的检查**：每条都能跑、都有自己的数字。**跑完把结果贴进回报。**
> ⛔ **任何一条不过 ⇒ 不许出现"完成 / 交付 / 实测通过"字样**（只能说"还没做完"，然后继续做）。
>
> 实测教训：上一条硬规则（§1.8 临时文件 / §2 允许差异 / §2 证据口径）**全都没配检查**，
> 于是违反它们**不留任何痕迹** → 交付时"看起来完全合规"。

> **这 8 条已做成脚本模板 → `reference/verify-template.md`**：新项目开工时复制成 `tools/verify.ps1`。
> **能算出来的东西不要写成规则，写成脚本 —— 规则会忘，脚本每次都会跑。**

| # | 检查什么 | 怎么查 | 通过标准 |
|---|---|---|---|
| 1 | **临时文件不许遍地** | `Get-ChildItem <项目根> -Recurse -Filter *.cs \| Where-Object { $_.FullName -match '\\(_dev\|_assets_src\|_assets_tmp)\\' } \| Measure-Object` | **0 命中**。探针 / 一次性脚本只许在 `<项目根>/.ai-tmp/test/`，**用完即删**（§1.8） |
| 2 | **硬规则命中归零** | 对**本项目业务源码**递归 grep：`Debug\.Log`、`Resources\.Load`、`PlayerPrefs`、`(?<!Game\.)Input\.`、`GameObject\.Find`、`FindObjectOfType`、`Instantiate\(`；另见下方「引擎自称」 | **除"已登记例外"外 0 命中**；有例外 ⇒ 必须能在第 4 条查到（`§1.11` 的例外通道） |
| 3 | **聚合文件自洽** | 读 `策划/验收表.md`：把「结论」列**自己数一遍**，与该文件里的汇总数字/统计段对比 | **汇总 = 表体**。不一致 ⇒ 有人改了表没改汇总 = 未做完（实测：汇总写"35 通过 / 7 不一致"，表体实为 39 / 3） |
| 4 | **差异与例外都已登记** | 打开 `策划/验收表.md` 的「允许的差异」小节 | 每条例外（**引擎能力未用** / 与 A 的不一致 / 未使用 A 的素材 / 违 §7 硬规则的调用）**都有一行：是什么 + 为什么 + 出处 + 何时消除**。清单为空 ⇔ 第 2 条必须 0 命中 |
| 5 | **引用路径可达、无悬空文档** | ① 验收表/文档里每个 `<路径>:<行号>`、每个函数名逐个 `Test-Path` / grep；② 查有没有交接/进度类文档 | ① **全部可达**（实测：证据指向 `tools/*check`，而宿主已搬到 `.ai-tmp/hosts/` ⇒ 证据链断裂，等于没证据）；② **不存在** `docs/交接-*.md` / `NEXT.md` / `docs/进度*.md`（§1.5 第 8 条） |

| 6 | **证据必须比代码新**（**但要按"因果"作废，不许一改就全废**） | 把每条"已实测"引用到的产物（截图 / 数值表 / 脚本输出）取 mtime，与该行所述**代码或资产**的 mtime 比较 | **产物 mtime 必须晚于被验证对象**；早于 ⇒ 该行证据作废并按"未验证"重判（§1.12 第 3 条）。**作废范围 = 这次改动真能影响到的那几行**（同模块 / 同一功能链 / 同一屏），⛔ **不是"工程里任何文件一变就全量作废"** |
| 7 | **一键复检入口存在且能跑** | 检查交付物里有没有 `tools/verify.ps1`（或等价脚本），并实际执行一次 | **存在 + 能跑 + 逐行输出 `PASS / FAIL / HUMAN-ONLY`**；缺 ⇒ 不许出现"完成"字样（§1.12 第 9 条） |
| 8 | **实现必须由执行者产出（不许主 agent 自己写）** | 取"本任务时间窗内被改动的实现文件"（`client/` 源码 + 关卡/场景数据 + 表 + 表现层），逐个到 `.ai-tmp/test/dispatch-log.tsv` 里找对应派活行 | **每个文件都能对上一条派活记录**（文件在派活行声明的范围内 + 该行时间早于文件 mtime）；**对不上 ⇒ 主 agent 自己动手了 ⇒ 违规**（§5 开工闸门）。⛔ 留痕文件本身不许事后补写 —— 补写同一件事会同时违反第 6 条（证据新鲜度） |

**新增/修改任何检查之后，必须做两次自检**（与第 11 条同一个道理：**会误报的检查比没有检查更糟**）：

1. **已知正确的样本必须 PASS** —— 拿当前工程的正常产物跑一遍，红的必须解释清楚；
2. **已知错误的样本必须 FAIL** —— 构造一个缺陷（临时去掉/改坏那件事），证明它真的抓得住；
3. **只会报红、不会报绿的新检查不许上线** —— 它会让人去修一个**不存在**的问题。

> 实测代价：一条新的"署名渲染"检查**取错了像素带**（量到屏幕顶部的 HUD 而不是底部那行），
> 在画面**明明正确**的情况下报了 4 条 FAIL ⇒ 又花一轮"自己量像素、证明是检查错"。
> 同一次事故的另一半：**旧检查只 grep 源码字符串** ⇒ 画面明明缺失/大小写不对，它却全绿。

**第 2 条的补充：引擎自称（`§1.6`，⛔ 这一条只能人工核对，不许拿具体名字当 grep 模式）**：

交付物（界面文案 / 标题 / README / 交付说明 / 注释）里出现的**引擎自称必须逐字是 `clover-engine`**。

- 查法：对交付物 grep `引擎|Engine`，**逐条人工核对**每个自称；
- ⛔ **不许**把某个历史自造名（如某次凭空编出来的"XX引擎"）写成 grep 模式 ——
  **自造名是无穷的，个案不是规则**：写死只抓得到历史那一次，下次换个名字照样漏；
  更糟的是会**假阳性**（万一用户点名要做的游戏本身就叫那个名字，会被当成 bug 改掉）。

**第 4 条的"例外通道"（补上原来缺的那条路）**：
本 skill 的硬禁令（如「⛔ 别用 `Resources.Load` 绕开 `Game.Res`」「⛔ 引擎有就用引擎的」）
**允许有例外，但必须落在 `策划/验收表.md` 的「允许的差异」小节里逐条登记**，
格式：`【例外】<行为> | 为什么必须这样（实测证据） | 出处（文件:行） | 何时能消除`。
只写在**代码注释**里 = 没登记 = 违规（实测形态：某项目若干处 `Resources.Load` 绕过 `Game.Res`、
若干处"不用引擎能力、改自写设施"，**理由在注释里写得很扎实，但一条都没进验收表**
⇒ 验收时无从判定这是"深思熟虑的例外"还是"偷懒"。
这正是"例外通道缺失"的代价：**没有登记处，例外就只能藏在注释里，等于不存在**）。

## §1.12 ★★★ 判定权与证据契约（**规则是软的，契约才是硬的**）

> 一句话：**规则是软的，契约是硬的。** 规则读完由执行者自判，所以能被解释着绕过；
> 本节只写"把判定权拿走"的条款。**教训与案例一律不写在规则层**（要写就写进 `experience/`）——
> 规则层只留祈使句，这是防止本文件臃肿的唯一条例。

**1. 判定权只有三个合法归属（执行者自己不是其中之一）**

| 判据类型 | 谁判 | 长什么样 |
|---|---|---|
| **可计算的** | 脚本 | 退出码 / 数值 diff / 存在性 / 时间戳；**通过 = 脚本输出 PASS，而不是"我看过"** |
| **参考物自带的** | 参考物自己 | 参考物文件里的几何、骨骼与顶点、贴图、动画序列与帧率、界面像素坐标、**常量表** |
| **只有眼睛能判的** | 人，或**真的能收到图像的执行者** | 同机位并排图上的"一致 / 差在哪"，见第 7 条 |

**任何以"我觉得差不多 / 我检查过了 / 应该没问题"收尾的结论，一律视为未验证。**

**2. "我验不了"必须是合法且必须的输出（这一条专治造假）**

- 执行者无法验证的项，**必须**以 `BLOCKED：<缺什么 / 谁能验>` 上交。
- **声称验证过自己无法验证的东西 = 本 skill 最严重的违规**（比"没做完"更严重：它污染后续所有判断）。
- **停止不罚，猜才罚。** skill 里一切"必须做完 / 不许停"的条款，**都不适用于"我验不了"这一情形** ——
  遇到验不了的项，正确动作是标记 BLOCKED 后继续做别的，而不是把它写成"已完成"。
- ⛔ 违反本条时，"我怕被判成没做完"**不构成理由**。
- ⛔ **报 BLOCKED 之前，必须先穷尽替代路径**，并在报告里列出：**试过什么 / 结果如何 / 为什么都不行**。
  允许说"这条路不通"，但**不许直接跳到"无解"** —— 先按降级链逐级找（§0.5 第 2 条是它的模板）。
  实测教训（匿名）：曾把"用户可能不是某个宿主"直接判成"只能人工降级"，
  而漏掉了**与宿主无关的通用层**（git hook / CI / 打包入口）。**"我没找" ≠ "不存在"。**

**3. 证据的定义（叙述文字不算证据）**

- 证据 = **产物**：截图、数值 diff 表、脚本输出**原文**、文件哈希、录屏。
- **执行者的文字叙述一律不算证据**（"已修复""已实测""确认一致"都只是叙述）。
- **证据必须比被验证的对象新**：交付前比对 mtime —— **产物 mtime 早于最后一次代码改动 ⇒ 该证据作废**。
  本条可脚本化，专治"拿旧图充数"。
  **口径按「批次」**（见 §1.13 四拍）：一批证据对应一个代码版本；该批之后若又改了代码 ⇒
  **只作废受影响的行**（真会被这次改动影响到的功能），其余批次证据仍然有效 —— 不必推倒全部重采。
  ⛔ 两个极端都不许：**不许拿旧图充数**，**也不许改一处就重采全部**。
- 引用必须精确到 `文件:行`；拿不出精确引用 ⇒ 该行按未验证处理。

**4. 基准必须来自参考物，不许来自我们自己的产物**

- **"产物 vs 产物"的自检等于零信息**（自洽只能证明自洽）。典型形状：拿"我们自己烘出来的数据"去比
  "我们自己从场景复算出来的数据"，永远通过，**再错也通过**。
- 每条自检必须写明**基准来自哪里**；基准说不清 ⇒ 该自检无效，结论按未验证处理。
- 参考物那一侧必须**先被解析出来并落盘**（几何、骨骼、贴图、常量、界面坐标…），作为该项目的唯一标准答案。
  （**用户明说不做复刻时**，唯一标准答案 = **用户规格书**，见 §0「用户**明说**不做复刻怎么办」 —— 但**仍然不许**拿我们自己的产物当基准：
  "产物 vs 产物"的自检照旧等于零信息。）

**5. 外观 / 手感 / 数值 不许"看起来合理"，必须写出来处**

- 一切**常量、坐标、比例、颜色、时长、曲线**必须能指到：参考物文件 + 偏移、参考物源码 `文件:行`、或参考物资源文件。
- **写不出出处的不许进代码。**"这个值看起来合理"**不是出处**。
- 没有出处时，正确动作是**去解析参考物**（解包 / 反编译 / 读数据），**不是自己定一个**。
- 参考物确实拿不到 ⇒ 按 BLOCKED 上交（第 2 条），并登记为"允许的差异"。

**6. 交付粒度：一个单元必须小到能被一条命令判生死**

- 禁止"一口气做完整个游戏 / 整张地图 / 全部界面"。**范围是所有约束的天敌**：范围一大，"差不多"必然蒙混过去。
- 每个交付单元自带一条**可执行的通过判据**（脚本 / 数值），不通过就不进下一个单元。
- 允许做很久 —— 靠**切片**跨过去，不是靠**砍范围**（见 §5 接力）。

**7. 外观验收的最低形式：同机位并排**

- 每个外观项 = 一组 **「参考物图 | 我们的图」**（**同机位、同分辨率、同画幅**）+ 一行
  `一致 / 差在哪 + 差多少`。
- **没有参考物那一侧，描述不算验收**（"画面里有一颗手雷"是描述，不是验收）。
- 动态项（手感 / 动画连贯 / 节奏）单帧判不了：要么逐帧录屏比对，要么把驱动它的**常量**与参考物对齐（第 5 条）。
- 终审是人：执行者可以产出逐元素比对记录，但**"像不像"的结论由人下**。

**8. 开工先验"感官通道"，不通就不许写感官结论**

- 任务含画面 / 声音时，**必须先用一张已知内容的图（或一段已知内容的音频）自检通道**：
  真的收到了内容，才允许写画面类结论。
- **读图返回占位 / 空 / 被省略时，立即停止写画面类结论**，改为 `BLOCKED：图像通道不可用`。
- ⛔ 实测形态（最贵的一种）：执行者连续几十次拿到"图像已省略"的占位文本，
  **仍然逐条写出了画面描述与"已修复"** —— 这些结论全是编的，且在验收表上与真证据看起来毫无区别。

**9. 交付必须带一键复检入口**

- 交付物含 `tools/verify.ps1`（或等价脚本），逐行输出 `PASS / FAIL / HUMAN-ONLY`：
  `PASS/FAIL` 覆盖一切可计算项（数值 diff、可达性、存在性、mtime 新鲜度、哈希）；
  `HUMAN-ONLY` 列出**只能由人或多模态判**的项，供人一次过目。
- 用户**只跑一次脚本**，不陪执行者逐点调参。**"用户不可能陪我一点点调"就是本条的存在理由。**

**10. 结构底线**

> **执行者永远不是最后签字的人。**

只要还有一条结论由执行者自己签，本 skill 的全部禁令都可以被绕过 —— 因为它们最终都靠执行者的判断兑现。
把签字权交出去（脚本 / 参考物 / 人），是唯一能被机器强制执行的约束。

## §1.13 ★★★ 改动回路：**批次流水线**（把贵的动作挤到最后，且只做一次）

> ### ⛔ T0（最高优先级 · 实测过的最大时间黑洞）：**取证是一次性的批量动作，不是逐行 / 逐片重复的实机**
>
> **一个交付单元（= 能被一条命令判生死的那一级）只许走一遍：编译一次 + 一条驱动链路按序跑完 + 采一次联络图。**
>
> - **验收表有 N 行 ≠ 要进 N 次实机**；**派了 K 个执行者也 ≠ 每个执行者各自进一次 Play** ——
>   验收行是"证据的**格**"，不是"实机的**次数**"：几十个格由**同一次**链路一次跑完，压进 2~3 张联络图。
> - 判据一句话：**凡"分钟级"的动作（编译 / 进 Play / 截图 / 跑生成器 / 出资产），在一次交付里只许做一次**；
>   之后再改代码 ⇒ **只重采"这次改动真能影响到的那几行"** ——
>   ⛔ "工程里任何文件一变就全量作废 / 全量重采"是错的（没有因果关系的行**不许**被作废）。
> - ⛔ **典型违规形状**：把"批量改 + 一次取证"拆成 N 轮「改一点 → 编译 → 进 Play → 截图」，
>   于是**总等待 = N × 分钟级**，其中绝大部分是**纯重复等待**。
>   **实测代价（匿名）**：一轮任务里把最贵的动作重复了十几遍，数小时里绝大部分是等待，
>   而正确形状是"全部改完 → 编译一次 → 一条链路跑完 → 采一次联络图"。
> - **判据不是"验得够不够仔细"，而是"最贵的动作被重复了几次"** —— 重复 N 次 ≠ 更可靠，
>   只等于把同一份验证做了 N 遍。
> - ⚠️ 本条**不是**让你少验：该验的格一个不少，改的只是**顺序与粒度**（下面四拍）。
>
> **为什么不"小步循环"**：编译是**分钟级**，进 Play + 注入按键 + 抢拍也是**分钟级 ×N**，
> 而"读数据 / 跑断言 / 数据 diff / 静态检查"是**秒级**。
> **改一处就编译截图 = 把最贵的动作重复 N 次** —— 实测量级：一个功能改 30 处 ⇒ 30 次分钟级等待，
> 其中 29 次是**纯重复等待**；若一路这么干，几百张截图、几百分钟全是等出来的。
> **正确做法：便宜的多跑，贵的攒一批只做一次。**
> ⚠️ 这**不减验证强度** —— 该验的项一个不少，改的只是**顺序与粒度**。

### 四拍（一个交付单元走完 ①②③④）

| 拍 | 做什么 | 代价 | 禁令 |
|---|---|---|---|
| **① 一次性取证**（只读） | 把依据一次查完（参考物数据 / 引擎 API 出处 / 现有代码现状），产出**改动清单**：改哪几个文件、每处改什么、**每处的判据是什么** | 便宜 | ⛔ 这一拍**不许写代码** |
| **② 批量改** | 按清单把改动**一次全写完**，中间**不编译、不截图** | 便宜 | ⛔ 不许改一处编译一次 |
| **③ 一次编译 + 预演** | 编译**一次**并确认成功 → 跑**廉价自检**（离线断言 / 数值探针 / 数据 diff / 静态检查）→ 一轮预演里挑出的问题**批量修** → 再预演一轮。**循环粒度 = 一轮预演，不是"一处改动"** | 中 | 编译失败 ⇒ ⛔ 不许测 |
| **④ 集中出证据**（贵，**只做一次**） | ① 先出**证据分格表**（格号 / 状态 / **类别：数值类·表现类** / 判据 / 期望值）→ ② 按分格表**一条驱动链路按序跑完** → ③ 采**一次联络图**（N 格拼一张，格上烧「格号 + 状态 + 关键数值」），脚本按格判定，**AI 只读这张汇总图** | 贵 | ⛔ 不许逐项进出 Play、不许逐行截图逐张读图；④ 后再改代码 ⇒ 只重采**受影响的行** |

**③ 必须产出一份「预演报告」**：逐项写清哪些"**已就绪、可采图**"、哪些仍有风险 ——
这样 ④ 一次就能采对，不会"采完才发现要改、改完再采一遍"。

### 截图的三个触发条件（**除此之外都不截**）

1. **交付前**：把 `表现类` 的行**采一次联络图** —— AI **只读这张汇总图**，⛔ 不逐张读原图；
2. **诊断态**：某个点**改了多次仍不对** ⇒ 截该处的**全图**排查（**这是截图最有价值的用法**）；
3. **判据本质是画面**（动画没播 / 贴图错 / UI 不可见）⇒ 必须看图，数值替代不了。

**为什么这么定**：截一帧是**分钟级**，而**AI 读一张图按像素烧 token** ——
「47 项 ⇒ 47 张图、逐张让 AI 读」比「47 项 ⇒ 2~3 张联络图、AI 读 1~3 次」贵**一个量级**；
而**判定本来就该由脚本做**，AI 只分诊（§1.12 第 1 条）。
联络图的格式、采集与判定规范见 `reference/visual-loop.md` 第八节。

### 五条硬不变量（一条都不许丢）

1. **任何实测之前，编译必须已成功**；编译失败 ⇒ **中止一切验证**。
   ⛔ 禁止在"编译失败"状态下继续测 —— 宿主可能仍在跑**旧程序集**，此时所有"实测"验的都是过期代码。
   （实测踩过：一次改动引入重复变量声明、编译失败被忽略，之后几十轮验证**全部无效**，还据此宣布修好了。）
2. **证据必须比代码新 —— 口径按「批次」**：一批证据对应一个代码版本；
   ④ 之后若又改了代码 ⇒ **只作废受影响的行**（真会被这次改动影响到的功能），其余批次证据仍然有效。
   ⛔ 不许走另一个极端（改一处就重采全部）。
3. **日志里的 Error / NullReference 当批次清零**：不许用"降频 / 忽略 / 不影响主流程"掩盖；
   每条都要有处置（修掉，或登记为已知并给出处）。
4. **收尾统计的是"错误总数"，不是"我没引入新错"。**
5. **采样器 / 驱动脚本：先自检，再上实机**（实测**近 100% 的"白等"**都出在这一步：
   跑一个场景是**分钟级等待**，自检是**秒级** ⇒ **自检不过，一次都不许跑**）。
   三条必过，代码与闸门见 `reference/verify-template.md` **第 14 项**（可直接抄）：
   - **语法**：`.ps1` 先过 `Parser::ParseInput`，**0 语法错误**；
   - **编码**：`.ps1` 要么**纯 ASCII**，要么**带 BOM**。无 BOM 且含 CJK 时 PS 5.1 按 **ANSI** 解析 ⇒
     **中文匹配静默失效**（脚本照跑、逻辑全错：实测把"已完成"读成"没完成"，**白等满超时**）⇒
     匹配用的中文字面量**一律用码点拼**；
   - **结束信号与超时**：完成判据**只能是被测程序自己写的标记**，且按"**新增次数**"判定
     （防读到上一轮的旧标记）；**超时只许当兜底，⛔ 不许当完成判据**。
     入口先验形状：如 `eval --code` 要 `return X;`，**裸表达式编译不过** ⇒ 健康检查恒为 false，
     会把**好好的 Play 会话**当成"引擎没起来"杀掉。
   - **读日志要 `FileShare.ReadWrite`**：游戏把日志**独占**持有，普通读法（`File.ReadAllText` /
     `-Raw` 默认共享模式）**每次读都抛 IOException** ⇒ 标记永远读不到 ⇒ **又白等满一次超时**。
     上面三条都只防"脚本自己写错"；这一条防的是**读别人正在写的文件**，同类还有：日志路径按**当天**取、
     写完立刻读要**重试**。
     6. **修 bug 的验证范围 = 这条 bug 的路径**（⛔ **不是"重跑全部场景"**）：
     ① **修之前先写一条能复现它的断言/探针** —— 否则你不知道修没修好、也不知道有没有把别处弄坏；
     ② 修完**只跑那条路径**，并**只重采它所在的行/屏**的证据；
     ③ **全量重采只有一个合法时机**：交付前最后一次（本节的 ④），或"改动确实横跨多个区域"。
     ⛔ 判据不是"多测一点更保险"，而是**成本硬账**：一个字段改动 × 全量场景 = **场景数 × 分钟级等待**。
     **实测（本 skill 自身的规则被我违反）**：四个点状 bug（一行文案颜色 / 一行落点坐标 / 一行判定 /
     一行写死的标签）触发了 **21 个场景的全量重拍**，用户原话：
     「**如果是 bug，验证对应的 bug 不就好了？？？？？**」——
     而本节第 2 条与 §1.12 第 3 条**早就写了**"只作废受影响的行、不许改一处就重采全部"。
     ⇒ 根因不是"不知道规则"，而是**规则没挂在动作入口上**（§0.6）：重采工具默认接受"一串场景"，
     于是"全量"是最省事的写法。
     **怎么才不靠自觉**：把"受影响的行/屏"做成**一份范围表**（`reference/verify-template.md` 第 6 项的
     area/panel 映射**就是**这份表）—— **重采工具只接受范围表算出来的场景**，
     闸门第 6 条按**同一份表**判过期 ⇒ 规则与检查共用一个数据源，
     就不会出现"一边写着按因果、一边全量重拍"。

     **「交付单元」的定义不变**（§1.12 第 6 条）：**能被一条命令判生死**的那一级（一个功能 / 一张表 / 一个面板），
**不是"一行代码"**。单元内部可以批量；⛔ **单元与单元之间不许跳过 ③④** ——
"批次"永远不是"攒着不验"的借口。

## §2 ★★ 交付闸门：一张必须填满的验收表（§1 的可执行形式）

**表在开工时就建好**：`策划/验收表.md`。**行 = 参考游戏 A 的系统清单**。
**没有 A 的系统清单 ⇒ 没有验收分母 ⇒ 必然会漏**（实测漏掉的全是"玩起来才知道"的：
踩敌、顶砖块出道具、火球、旗杆通关、暂停菜单、双人模式）。**表里出现空行 = 没做完 = 不可交付。**

### 1:1 复刻硬标准（用户点名 A = **默认就是 1:1**，不是"像"）

> 用户原话（投诉）：**「我要的 1:1 复刻……素材都是错了，按钮样式地图什么都是乱七八糟的」**。
> 病根：**把验收标准写成"像不像"**。像 ≠ 1:1。**只要用户点名了 A，默认就是 1:1 复刻**，
> 除非用户明说"风格参考就行 / 不必一致"（例外登记同 §0 硬规则 6）。
> **用户明说不做复刻 ⇒ 本节不适用**：改按《**原创规格**》逐条判（判据强度不变，只换标准答案来源 —— 见 §0「用户**明说**不做复刻怎么办」）。

| 维度 | 1:1 的**硬要求** | 常见违规（都算不可交付） |
|---|---|---|
| **布局** | **逐元素对齐 A 的原版画面**：位置/尺寸/层级/间距按原版像素（用**同一分辨率基准**换算），并用原版截图并排比对 | 自己"设计"了一版顺眼的布局；元素居中/靠边"差不多" |
| **素材** | **必须用 A 原版的素材**（来源与穷尽标准见 **§4 闸门 3**）。**占位色块 / 通用素材包 / 自画近似图 = 不可交付** | 用 KayKit/Quaternius/内置几何体凑；占位色块当成品交 |
| **字体** | A 的原版字体（位图字体就用位图字体；中文用 A 中文版字形），字号/字距照原版 | 用引擎默认字体顶替，还自称"一致" |
| **色调/亮度** | 照 A 原版；**不许自己提亮/压暗/加滤镜** | 面板被颜色乘数压暗或自己调亮，却当"修好了" |
| **交互细节** | 按钮的常态/悬停/按下/hover 高亮、光标形态、音效时机，逐项对齐 | 只做"能点"，不做原版的视觉/听觉反馈 |
| **节奏** | 动画速度、升级速度、任务长度按原版量级 | 随手调参 |

**对照方法（不作为"看过一眼"就算）**：
① 以**同一分辨率基准**截原版图与自己的图；② 逐元素列表比对（位置/尺寸/素材/字体/颜色）；
③ 每项只允许写 `一致` 或 `不一致（差在哪）`；④ **出现任何"不一致"⇒ 该版本不可交付**，改完重截再比，循环到全一致。
⑤ **允许的差异清单默认是空的** —— 想加例外，必须在 `策划/验收表.md` 里逐条写明并说明理由。
   这份清单**同时**是「引擎 API 例外」的登记处（违 §7 硬规则的调用、不用引擎能力的自写设施），
   格式与检查见 **§1.11 第 4 条**。**只写在代码注释里 = 没登记 = 违规。**

**交付物必须含「原版对照表」（`策划/对照表.md`）** —— 它是 §0.5 的执行形态：

每行 = 一个元素：`元素 | 原版值（含出处：文件:偏移 / 源码 文件:行 / 图片坐标） | 我们的值 | 差值`。

- **差值为 0 才算过**；写不出原版出处的那一行 = 该元素未验证。
- 覆盖范围至少：几何与碰撞（含**通行性**）、模型与动画数据、贴图、界面元素的坐标/尺寸/颜色、数值与公式。
- **表里没有的行，等于这个元素没人搬过** —— 不允许"实现了但没进表"。

**硬性判定**：

1. 任何一行「结论」为空 / 写着"未验 / 待验 / 下次补" ⇒ **禁止出现"完成 / 交付 / 实测通过"字样**。
2. **"说完成"与"列未验项"不许出现在同一条回复里。**
3. **证据按「类别」给，不搞一刀切** —— **每条验收行必须在表里标出它属于哪一类**：

   | 类别 | 包含什么 | 判据 |
   |---|---|---|
   | **`数值类`** | 数值 / 逻辑 / 状态 / 坐标 / 计时 / 计数 | **运行时日志行 + 断言输出**（实机跑出来的），⛔ **不需要截图** |
   | **`表现类`** | 动画有没有播 / 贴图对不对 / UI 可见与对齐 / 颜色 / 时序观感 | **交付前必须进一次「联络图」**（见 §1.13 第 ④ 拍），且**格号要能在图里查到** |
   | **`性能类`** | 帧率 / 帧时间 / 掉帧 / 卡顿 | **帧时间** 与 **渲染设备名**（`SystemInfo.graphicsDeviceName`）**必须同时给** —— 设备是 `Microsoft Basic Render Driver` 时是 WARP 软件渲染，**数字无意义、不许拿它下任何结论**；配方与实测数字见 `experience/perf-triage.md` |

   ⚠️ **这条的判据是"证据真的跑出来过"，不是"每行各跑一次"** —— **一个交付单元只进一次 Play**：
   用**一条驱动链路按序把该单元的所有格跑完**，再采**一次**联络图（见 §1.13 的 **T0** 条）。
   **验收表有 N 行 ≠ 要进 N 次实机**；⛔ 也**不许**改一处就全量重采。
   一次性行为（死亡 / 通关 / GameOver）要在**那一次**里真的触发一次。

   ⛔ **两个极端都不许**：
   - **不许逐行截图、逐张让 AI 读** —— 「47 项 ⇒ 47 张图」比「47 项 ⇒ 2~3 张联络图」贵**一个量级**
     （截一帧是分钟级；**AI 读一张图按像素烧 token**）；
   - **不许把 `表现类` 用数值代替** —— 实测事故：数字全对（`分数=000200 金币=×01`）而**金币动画根本没出来**。
     **数字对 ≠ 表现对。**
4. **禁止挑有利证据**：拍到坏图必须写清"坏在哪 + 改了什么 + 重拍图"。
5. **用户报的问题一律视为"表里漏了一行"** → 回去补表并把同类问题一起排查，而不是只修那一个点。

> 完整模板与判定细则见 **`reference/game-delivery.md` §1**。

## §3 ⛔ 开口前闸门（**开工前一次性澄清**；之后只有两种能开口）

**能开口的只有两种**：
① **被阻塞** —— 缺一样**只有用户能给**的东西（密码 / 参考游戏名 / 用户亲手打开编辑器 / 用户点同意）；
② **全部做完** —— `策划/验收表.md` **每一格都填满**，且每格的证据我都**自己读过**。

**其余一切句子一律删掉、继续做** —— 包括「要不要 / 接下来 / 进度 / 还需要我 / 你看行吗 / 计划 / 待办 / 还差几步」，
**也包括回合结束时的收尾**（回合长度上限不是开口理由；下一轮直接从下一个动作继续，不复述不求许可）。

**判据是产物不是自觉**：没到 ② 之前，出口的句子里不许出现「完成 / 做好了 / 实测通过」。
违规长什么样：见 §1 违规表（问"要不要继续"= 做一点交一点同罪）。
「该不该做某一部分」不许问用户 —— 参考游戏有的就得做 ⇒ **自己定**（§0 硬规则 3）。

### 开工前的澄清窗口（**唯一被鼓励的"多问"**）

> **"不许乱问"指的是不许问进度/许可，不是不许问清需求。** 开工前问清事实，是省掉最贵返工的手段。

- **时机**：接到任务、**还没写第一行代码 / 还没建工程之前**，允许把"不问就会做错"的问题**一次问完**。
- **形式**：**攒成一批、编号提问，一次发出**（一次 ≤ 5 条，每条给默认选项或候选）；**问完就开工**。
- **该问的**（问的都能落进文档）：参照**哪一款**具体的游戏 / **形态**（单机·联机·单机+联网）/ 目标平台与**分辨率基准** /
  范围边界（做到哪个场景为止）/ 素材能否用**用户本机文件**（如 MPQ·CASC）/ 有没有必须对齐的**硬指标**（时长、帧率、语言）。
- **不该问的**：参考游戏里有的功能（**直接做**）/ 我们内部的技术选型（**自己定**）/ "先做哪块"（**自己定顺序**）。
- **只开一次**：澄清窗口用完即关 —— 之后新出现的"只有用户能给"的阻塞仍可按 ① 问（如用户来打开编辑器），
  但**不许拿问题当拖延或征求许可**（"我先做 A 还是 B？你定" = §1 违规）。
- **答案必须落盘**：问到的结论写进 `策划/策划案/{A}参考规格.md`（形态 / 范围 / 基准）
  与 `策划/验收表.md`，**后续全程照它执行、不许再反复确认**。

> **适用范围**：本闸门管的是「**向用户**开口」。
> **子 agent 不在此列** —— 子 agent 必须把结果回报给调用方（主 agent），那是它的职责，不算违规。
> 子 agent 的回报格式见 `patterns/multi-agent.md` 第 3 步。

## §4 ★★★ 做游戏的四道硬前置闸门（不通过就停，不许自己绕）

**不通过任何一条，后面的工作都会白做。**

### 闸门 0（**最先做**）：判定游戏形态 —— **单机** / **网游** / **单机+联网**

> **动手第一件事不是建工程、不是查环境，而是判定这个游戏"该不该有服务端"。**
> **判错了方向，后面全白做**（单机被当成联服 = 反复探测本地服务器、建一堆用不上的 Go 代码；
> 联机被当成单机 = 静默降级、核心玩法没了）。

| 要判定什么 | 怎么判 |
|---|---|
| **形态** | ① **单机**（纯本地，无任何网络）② **纯网游**（没服务器玩不了）③ **单机为主 + 联网功能**（原版两种模式都有） |
| **联网方式**（仅 ②③ 需要） | 权威服务器 / 局域网 / P2P / 大厅+房间 / 直连 IP / 云存档 |
| **依据从哪来** | **① 原版游戏本身是什么形态（第一依据，先联网搜清楚）** → ② **用户这一轮明确写了**什么（"联机 / 多人 / 服务器 / 对战 / 排行榜 / 联机版"）→ ③ 两者都没有 ⇒ **按原版形态做** |

**硬规则**：

- ⛔ **禁止"默认按联服处理"**，**禁止"需求没提就一律去查服务器环境"** ——
  这正是用户多次投诉的那句话：**"做个单机一直测网络，是不是有病"**。
- **原版是单机的游戏就做单机**（马里奥 / 俄罗斯方块 / 祖玛 / 单机 RPG / 单机策略…）：
  **不建 `server/`、不调 `CloverNet.Init`、不查 etcd/redis/mysql、不跑 `env.exe`、交付说明首行标注「单机版」**。
- 只有**用户明确说了**联机/多人/服务器/对战/排行，**或原版本身就是纯网游**（MMO、对战竞技）→ 才走联服。
  **原版同时有单机与联机两种模式时（如暗黑2）**：默认做**单机模式**（它是原版的一等公民），
  **除非用户点名要联机**。
- **拿不准 → 先联网搜一轮原版形态**（`<游戏名> single player or multiplayer` /
  `<游戏名> 是单机还是网游`），**仍拿不准才问用户一句话**。
  **禁止"一边不确定、一边反复探测本地服务器环境"**。
- **判定结果写进** `策划/策划案/{A}参考规格.md` 顶部的「**形态**」一节；
  **只判一次，全程照它执行** —— 不许中途反复改变、也不许反复自检。
  **形态一旦判为单机，"服务器环境自检"这一整段动作在本次任务里不存在。**

### 闸门 1：动手前先确认 **360（及同类国产杀软）已关闭**

**开工前先问用户一句「360 关了吗？」** 用户说没关 → **别创建工程**；**不确定 = 按没关处理**。
（360 会让 `Unity.Licensing.Client` 通道永远拒绝连接，编辑器每次重连烧 60 秒并循环 ——
**那不是慢，是根本起不来**。详见 `reference/pipeline-and-unity-cli.md` §1。）

### 闸门 2：创建完 `client/` 后，**让用户自己在编辑器里打开它；用户不开，就不继续做**

```
① AI 建工程目录 + 写好全部代码 + 生成器
② AI ★【在让用户添加项目/打开编辑器之前】把 com.unity.pipeline 写进 Packages/manifest.json
③ AI 才让用户去「添加项目到 Hub + 打开编辑器」，并给出可照做的 Hub 步骤
④ 用户打开（只能用户做）
⑤ AI 驱动那个活着的编辑器
```

**硬性禁止**：

- ❌ 创建完工程后自己跑 `unity run` / `unity test` / `Unity.exe -batchmode` 去"顺便"编译验证
  （首次导入把一次往返拖到十几分钟，且授权/杀软任一环出问题就是静默卡死）。
- ❌ 用户没打开编辑器就"先跳过实测，把代码交了"。
- ❌ **用户不开编辑器，还继续往下做** —— 正确动作是**停下**说清"我需要你打开 `client/` 文件夹"，然后**不继续**。
  **没有例外**，即使用户说"你自己跑别烦我"也不做（批处理模式 `-executeMethod` 执行完立刻退出、进不了播放模式，
  既慢又验不了画面）。
- ❌ **在 Editor 脚本（生成器 / 构建器 / 批量工具）里调用任何会弹「原生模态对话框」的 API**
  （`EditorSceneManager.SaveCurrentModifiedScenesIfUserWantsTo()` / `EditorUtility.DisplayDialog*` /
  模态 `EditorWindow` …）：无人值守驱动时它会**阻塞编辑器主线程**，把 Pipeline 连同后续**所有**命令
  一起拖成"静默卡死"（`/api/status` 仍 ready、`/api/dialog` 看不到、进程 CPU 差值 = 0 —— 见 **P-5**）。
  "当前场景可能有未保存修改"一律**静默处理 + 打 Warn 日志**。

> Hub 添加步骤话术、P-0~P-5 全部踩坑（含 `unity status` 空表 / **Editor 脚本弹原生模态框把编辑器卡死** /
> 失焦不 tick / 域重载 / 按键注入"完全没反应"）
> 见 **`reference/pipeline-and-unity-cli.md`**。**遇到连不上、卡死、第二次进 Play 全蓝时去查它。**

### 闸门 2b：**每一条 `unity` 命令都必须在「Unity 工程目录」里执行**（前置，不是排查手段）

`unity` CLI 的编辑器发现是**相对 cwd** 的 —— 它只去 `<当前目录>/Library/Pipeline/.unity-pipeline-port`
找描述文件。**在工作区根 / 上一级 / 别的项目目录里跑 `unity`**，它不会报"目录不对"，只会
找不到编辑器（或去折腾别的工程）⇒ 你会把"我目录错了"误判成"包装晚了"，白让用户重启一次。

- ✅ **唯一合法形态**（二选一）：① `Set-Location "<项目根>/client"` 后跑；② **每条**命令都带
  `--project-path "<项目根>/client"`（**不能只带第一条**）。
- ⛔ **禁止**：在**工作区根**（所有 `clover-*` 项目并列的那一层）里跑任何 `unity` 命令；
  用 `cd ..` 之类**相对路径**跳目录后再跑 —— **一律写绝对路径**。
- **证据要求**：拿 `unity status` 当"编辑器活着"的证据时，必须**同时**给出「工程路径 = `<项目根>/client`」
  这一项（只有 `ready` 不够 —— 它可能在报另一个工程）。
- **空表 ≠ 包装晚了**：先按本条自查目录，**再**谈重启编辑器（P-0 → P-1 的先后见 reference）。

### 闸门 3：素材**必须先用参考游戏 A 自己的**（本条只管"从哪来"；"不许换素材"见 §0）

**素材是"一眼认得出这是 A"权重最大的项。**
（用户原话：**"skill 不是让你先找相关的素材吗？你怎么默认使用通用素材了！"**）

**硬规则**：

- **级 ①「A 自己的素材」= 唯一首选**：原版 / 同源 / 复刻 / 官方 SDK / mod 工具 / 社区提取 / rip。
- **"穷尽"的量化定义（达不到就不算找过）**：**≥ 4 轮**不同关键词（中英各半）×
  **≥ 3 类站点**（GitHub / Gitee 与镜像 / 素材站如 spriters-resource / 论坛贴吧 NGA 3DM 游侠 / CSDN 爱给 网盘直链）×
  换过**格式与打包方式**（sprite sheet / 单帧 PNG / 模型 FBX·GLB / 贴图 / 音效包 / MPQ·CASC 解包产物）。
- ⛔ **在 ① 穷尽之前，禁止下载、禁止接入任何通用兜底素材**（KayKit / Quaternius / Kenney / 内置几何体…）。
  **不许用"先做起来 / 别停工 / 能用就用 / 为了效率"当跳级理由** —— 那是偷懒，不是效率。
- **调研必须落盘**：`策划/素材调研.md`（每轮：搜了什么词 / 看了哪些站点 / 拿到什么 / 为什么不可用）。
  **没有这份文件 = 素材闸门未通过，不许开始接资源。**
- **A 的素材需要"用户本机游戏文件 / 登录 / 会员 / 付费 / 点按钮"时 → 走级 ④：先给用户清单并等用户**，
  **不许自己跳过 ①**。Blizzard 系（MPQ/CASC）即此类：解包工具链公开，但**游戏本体文件只有用户有**。
- **级 ③ 兜底素材只有前两级"真的做不到"时才允许**，且必须同时做三件事：
  ① `策划/素材调研.md` 写清"①② 为什么都拿不到"；② **交付说明首行**高亮
  「⚠️ 未使用 <A> 的素材（原因：…）」；③ `client/资源欠缺清单.md` 登记"待换成 <A> 的素材"。
- **禁止把"下不动"说成"没有"**：换镜像 / Gitee 同名仓 / 压缩包直链 / 论坛附件 —— 都试过才算"拿不到"。
- **许可不设门槛**（非商用）：rip / 社区提取 / 来源不明**都能用**，能下就用，记一行来源即可。

> 详细分级、站点清单与"让用户下"的清单模板见 **`patterns/game-demo.md` §4.0** 与
> **`reference/asset-sources.md`**。

## §5 ★★★ 谁来做（主 agent / 子 agent 分工）

> **主 agent：探环境 → 定契约 → 派活 → 验收。它不做实现。**

### ⛔ 开工闸门：动手前先回答一句话（**不回答就不许调工具**）

**你接下来这次调用，属于哪一类？**

| 类 | 长什么样 | 谁做 |
|---|---|---|
| ① 探环境 | 只读：读文件 / grep / 跑只读命令 / 起编辑器看状态 | 主 agent |
| ② 定契约 | 写《步骤文档》《任务书》，或改 skill / 规则层 | 主 agent |
| ③ 派活 / 验收 | 发任务书、跑闸门脚本、采证据、对账 | 主 agent |
| ④ **实现** | **任何产出"工程产物"的写入**：业务代码、关卡/场景数据、配表、表现层、素材搬运、探针与闸门脚本的一次性改动 | **执行者（子 agent）** |

**① ② ③ ⇒ 做。④ ⇒ 立刻停手**：把它写成任务书（`scaffold/agent-impl.md`）派执行者，
主 agent 只保留"定契约 + 验收"。

**⛔ 例外：小改动主 agent 直接做**（**用户优先**，且这条是为了不把机器空转）：

下面三条**同时**成立 ⇒ 属"小改动"，**主 agent 自己做，不许派活**：
1. **改动面小**：**单文件**、且**净增删 ≤ 20 行**；
2. **不新增行为 / 不改数据格式 / 不新增资源**（只是改文案、改坐标、改常量的值、补一行漏掉的调用）；
3. **用户本轮明说**（"就一行文本""修个 bug""你自己改"）**或**用户报的是一个"点状缺陷"（某一处少了一行/写错一个字）。

**留痕方式**：在 `.ai-tmp/test/dispatch-log.tsv` 里写**一行**：
```
# direct-fix: <相对路径> -- <一行理由>; 用户原话="<用户怎么说的>"
```
闸门第 15 条按"具名裁定"通过它（**不要求派活行**）。
⛔ 不许拿"小改动"当**大改动的挡箭牌**：改了 3 个文件、或动了数据格式、或新增了行为 ⇒ 回到 ④ 去派活。
⛔ 判据是**改动面**，不是"我觉得简单"（"顺手把这块重构一下"= 大改动）。

> **实测代价（这条为什么必须写）**：用户说「**不就是加一行文本吗**」的那种改动，被按 ④ 走了完整流程
> （任务书 → 留痕 → 派活 → 等同步子 agent → 验收 ⇒ 每个子 agent 100~250 次工具调用），
> **一行文字耗掉半天**，用户原话：「**只是加一行文字，你搞了5个小时都没完事**」。规则的本意是省预算，
> 结果在"一行文本"上把预算全烧在流程里 —— **省预算的规则不能比它省的东西更贵**。

> **判据不是"我能不能做 / 快不快"，而是"这一步属不属于实现"** —— 只要产物是工程的一部分，就是实现。
> ⛔ 特别提醒：**"顺手改一下"也是实现**（改一个数值、挪一格瓦片、修一行贴图名都算）。
> ⛔ **"改数据文件"（关卡 txt / 表 / 场景）同样是实现** —— 它最容易被当成"我没写代码"，从而绕过本节。

**⛔ 留痕（可机械对账，收尾自检第 8 条会查）**：每次派活后往
`<项目根>/.ai-tmp/test/dispatch-log.tsv` 追加一行：

```
<ISO 时间>\t<执行者名>\t<任务书路径或一句话>\t<预计改动的文件/目录>
```

收尾时拿它和"近期被改动的实现文件"逐条对账：**对不上 ⇒ 主 agent 自己动手了 ⇒ 违规**。

> **为什么补这道闸门（实测代价，匿名）**：本节早就写明"主 agent 不做实现"，
> 甚至写明"宿主对本任务的模型请求有硬上限（本机实测 500）"——**但闸门没挂在动作入口上**。
> 结果某轮主 agent 一个人连续改了几百处（关卡数据 / 表现层 / 流程 / 一次性脚本），
> **把 500 轮预算打满，任务在"做到一半"时被宿主强制暂停**，用户当场质问：
> 「就是让你避免这个问题才子 agent 执行的啊？skill 写的有问题是吗？如果有问题你就去改 skill」。
> 根因不是"不知道规则"，而是 **§0.6 那句话在规则自己身上没被执行**：
> **提示词是请求，闸门才是保证** ⇒ 所以补的是 ①**动作入口的一句话闸门** ②**可对账的派活留痕**。

> **⚠️ 子 agent 读到本节时**：你不适用这条 —— 你是**执行者**，要下场干活、而且要干到底；
> 唯一的限制是**不许再派生下一层**（见 `patterns/multi-agent.md` 第 4 步）。

| 情况 | 谁做 |
|---|---|
| **新任务**（实现一块功能 / 一个模块） | **派子 agent**（定义模板见 `scaffold/agent-impl.md`） |
| **修 bug —— 原执行者还能找回来** | **交回原执行者**（先按下面「派生方式」的硬规则确认通道正确；历史能恢复就恢复，恢复不了就在任务书里交接"上一棒做到哪"） |
| **修 bug —— 原执行者找不回来** | **主 agent 自己搞**，或照同一份 agent 定义开一个新执行者 |
| 探环境 / 定契约 / 写《步骤文档》/ 验收 / 裁决契约冲突 | **主 agent 自己**（不可下放） |

**⛔ 派生执行者的方式（硬规则：方式错了 = 换了个模型干活）**

1. **只许走「普通子 agent」通道**（给 agent 名 + 任务书）—— 这是唯一能让 agent 定义里的
   `model: inherit` 生效的方式，**执行者必须与主 agent 同模型**。
2. ⛔ **不许用「异步成员 / team / 带成员名」这类派生通道** —— 它**绕过 agent 定义的 `model` 字段**，
   把执行者落到**默认（auto）模型**。后果不只是"模型不同"：默认模型往往更弱，
   会把"照任务书干活"退化成"自由发挥"，回报格式、自检、临时文件位置这些约束会跟着一起松掉。
3. **每次派活后 10 秒内核对一次**：执行者用的模型 == 主 agent 的模型。
   只要不是（例如显示 `auto` / `default`）⇒ **立刻中止该执行者**，换正确通道重派。
4. **中止 ≠ 白做、也 ≠ 停工**：先让执行者把进度落盘、回一条简短回报，
   再把**已完成的成果**交给新执行者接力。⛔ **不许回滚已落盘的产出**。
5. **一次派一片**：普通子 agent 是同步的（派活 → 等回报 → 验收 → 再派下一片）。
   ⛔ 不许为了"并行快一点"改用异步通道 —— 省下的那点时间远不值模型不一致的代价。
6. **⛔ 执行者不许改任何 skill**：任务书里**逐字写上** —— 项目级 `<项目根>/tools/ai-skill/`、
   仓库里的全局源 `ai-skill/`、宿主的安装副本（`<宿主>/skills/ai-skill/`）**全都不许改**；
   发现 skill 里有错 / 过时 / 缺内容 ⇒ **写进回报，由主 agent 改**。
   （实测代价：有执行者顺手改了全局 skill 的能力表 —— 内容本身可能没错，但主 agent 与后续执行者
   会在**一个没人知情的基线**上继续判断，比改错更麻烦。）
7. **⛔ 派活失败 / 拿不到回报 ⇒ 先查盘，两次为限**：
   派活调用返回失败（`No result found` / `aborted` 之类）时，**⛔ 不要立刻重派** ——
   先去盘上查它**是不是已经落地了**（相关文件的 mtime / 内容 / dump / 截图）。
   **落地了就按"已完成"验收**（**回报丢了 ≠ 活没干**）；只有确实没落地才重派。
   **连续两次拿不到可用回报 ⇒ 主 agent 直接接手干完**（此时"不许自己实现"让位于"把事做完"），
   并在留痕里写 `# takeover: <原因>`。
   ⛔ 不许无限重派、⛔ 也不许把用户夹在中间等。
   （实测代价：两次派生都"失败"，而执行者其实**已经把活干完、只丢了回报**；
   主 agent 既没查盘又反复重派，白耗数小时、还去问用户 —— 用户原话：
   「**就改了署名，修个bug怎么这么麻烦啊**」。）

> **为什么写死这一条（实测出处）**：有人为了并行，用异步成员通道一次派了两片执行者，
> 执行者的模型落到 `auto`，被用户当场揪出来：「**为什么要建立 team？team 模型是 auto 啊。
> 你要用和你一样的模型！**」——**当时 skill 里并未写这条**，是事故把它补上的。
> 判据一句话：**派生完先看模型；不是主 agent 的模型，就是错了。**

**为什么主 agent 不做实现**：宿主对「单个任务」的模型请求数有硬上限（本机实测 500）。
主 agent 自己实现，几百轮就撞墙、手里只剩半成品；只派活则 **500 轮能管 25~50 个子任务**。

**为什么修 bug 优先交回原执行者**：它带着当时的全部上下文，比重新交代一遍便宜得多。
**上下文真丢了就别硬重建** —— 主 agent 自己搞更快。

**跨上限靠「接力」，不靠「砍范围」**：详见 `patterns/multi-agent.md`「轮次预算与接力」。

## §6 ★ 动手前两件事

**第一件：混合模式找依据（六处同看 + 联网；用户 > 引擎 > 联网/自创）**

要做一个逻辑时，**并行看这几处**（⚠️ **不是串行漏斗** —— 别"① 没有就看 ②、② 没有就算了"）：

| 看哪里 | 回答什么 | 优先级 |
|---|---|---|
| **本项目自己的 skill** / **本项目自己的文档** / **本项目自己的源码** | 这个项目的约定、打算怎么做、既有写法 | 🥇 **最高** |
| **引擎源码** / **引擎文档** / **引擎 skill（含本 skill 的 patterns）** | 能力的真实签名与行为、机制、通用做法 | 🥈 **其次** |
| **联网搜索** | 没见过的问题的通用解法、报错含义、版本差异 | 🥉 **再次** |
| **自己设计** | 以上都没有 | ✅ **允许** —— 但要**标注"本项目新增"** |

**冲突时以谁为准：用户 > 引擎 > 联网/自创。**

> ### ⛔ 红线：「用户源码」= **本项目自己的**源码。别人的 `clover-project-*` **不许看、不许抄**
>
> 工作区里经常同时摆着好几个 demo 工程（`clover-project-xxx/`，各自带 `client/`、`tools/ai-skill/`、
> `策划/验收表.md`、`Assets/Editor/*.cs` 生成器、素材目录…）。**做新项目时，它们不是依据，是污染源。**
>
> **禁止**（针对**新建项目**）：
> - ❌ 打开 / 读 / grep / 参考工作区里**不属于本项目**的任何 `clover-project-*` 目录
>   （源码、Editor 脚本、`tools/ai-skill/`、`策划/`、`docs/`、素材，全算）；
> - ❌ 照抄它们的目录结构、模块/面板命名、验收表、工程生成器、配表、写法与素材路径；
> - ❌ 以"隔壁项目就是这么做的"为由决定本项目的任何设计。
>
> **允许抄的只有两处**：① **本项目自己**的 skill 与源码；② 引擎源码 / `clover-doc` /
> 本 skill 的 `patterns`、`scaffold`、`experience`（**通用形状**，且示例代码不得当 API 用）。
>
> **新项目的一切从 0 自己设计** —— 目录、模块、面板、生成器、配表、素材来源全部自己定，
> 新引入的东西在交付说明里写清"**本项目新增**"。
>
> **唯一例外**：**用户在当前这一轮明确点名**「参考 / 沿用某个已有工程」——
> 那时才允许，且**只在点名范围内**（没点到的部分照样不许看）。

**看完仍没有现成的 ≠ 不做了**：可以① 用通用原语自己拼、② 联网找成熟方案读懂后落地、③ 自己设计。
**唯一不许的是"编"** —— 任何 API / 类名 / 字段名都必须能指出出处；
你新引入的东西必须写清"这是新增能力"，**不许让它看起来像引擎既有 API**。
（详见 `reference/workflow-and-standards.md` §1。）

> ### ⛔ 「引擎」这一档里最常踩的：写通用设施前必须先查引擎能力表
>
> **动手写任何"通用设施"之前，先过一遍 `reference/engine-mental-model.md` §4 的能力表。**
> 这十类一律先查：**UI 构建 / 对象池 / 存档·设置 / 图集 / 本地化 / 配表 / 动画 / 相机 / 场景 / 音效**。
> **引擎有就用引擎的，禁止重造轮子。**
>
> **实测代价**：一个项目手搓了 7.7KB 的 `UIBuilder`（节点/文本/按钮/铺满全自己写），
> 而引擎的 `UIWidgets` 里**这些全都有**（含专门的 `Stretch(rt)`）—— 不但白写一遍，
> 还因为"面板根节点没铺满"踩了坑，**而引擎的 `Stretch` 正好能防住它**。
> 病根是当时那张能力表**只列了 5 项、漏了 UIWidgets/对象池/Setting/图集/配表** ⇒
> **清单不全 = 业务必然重造轮子**。
>
> **表里没写到的通用需求 → 先去引擎 `Runtime/**` 搜一遍再动手。**

**第二件：策划自审** —— 动手前先出《行为 → 表现规格》表（每个行为在**画面/动画/声音/UI·数值反馈/网络**上分别是什么）；
**不知道就去搜参考游戏**；表里出现"占位 / 后续替换 / 留钩子" ⇒ **视为没做完**。
（详见 `reference/game-delivery.md` §5。）

**图片需求是硬闸门**：不能读图 ⇒ **立即停下**，请用户换多模态模型或先转写成文字方案；
能读图也要**先转写成文字方案**再动手；图片是需求输入，**不是美术素材**。
（详见 `reference/game-delivery.md` §7。）

**不确定时按四级查**：项目 skill → clover-doc → 源码 → 问用户。**硬约束：不许编造任何 API**
（任何 API 名必须能指出出处，指不出 = 不许写）。**没搞懂调用链不许动手。**
（详见 `reference/workflow-and-standards.md` §2。）

## §7 错误处理与日志（硬约束，服务端 + 客户端都适用）

> **凡是"没按预期走"的分支，必须留下一条日志。** 不写日志的失败 = 将来无人能查的事故。

- 必须打：出错返回 / 兜底判空 / 参数校验失败 / 非法状态 / `switch` 的 `default` /
  客户端网络·反序列化·资源加载失败 / 高频回调里的异常（**防刷屏：只报一次或降频**）。
- 用什么打：服务端 `logger.Infof/Warnf/Errorf`；客户端 `Game.Logger.Info/Warn/Error(tag, msg)`。
  **禁止**服务端用 `log.Printf`、客户端用裸 `Debug.Log` 打业务日志。
- 日志必须带可定位信息（谁 / 哪个消息号 / 关键参数 / 期望 vs 实际）、前缀统一。

> 完整清单与收尾自检见 `reference/workflow-and-standards.md` §3。

## 交付形态：游戏 = 「原版级完整成品」

**三段式交付，缺任一段 = 没交付**：
① 启动与菜单链路（启动画面 → 主菜单 → 创角/选角 → 读条进图）
② 首场景 / 首关卡完整版（场景·操作·相机·动画·UI/HUD·战斗闭环·音效·复活·结算）
③ 游戏内流程（暂停·设置·结算·回主菜单·退出）

**按 A 的系统清单逐项做完、禁止砍；出现空行 ⇒ 没做完**（清单怎么列见 `patterns/game-demo.md` §0.0c）。
**一律不许砍范围**（时间 / token / 规模 / agent 数量都不是理由）；**允许做很久，但必须充分测试**。

## 项目脚手架与配表

- **目录结构**（`tools/ai-skill/`、`server/`、`client/Assets/Scripts/{Def,Core,Network,...}`、`策划/`）

## 何时使用

用户出现以下意图之一时使用本 skill：

- **服务端**：新增/修改 C2S / 回包 / 推送消息号；编写 handler 并挂载；定义数据 schema；编写定时器、
  跨服事件、跨服查询；signup / login 鉴权；支付回调 / 订单（**订单归账号服**，见 `patterns/auth-server.md` 模板 4）。
- **客户端**：新增/修改客户端消息监听；编写网络请求；实现 Entity-View 绑定；配置 WorldSync；
  编写 UI 界面；使用资源加载、状态机、事件总线、定时器。
- **整体功能原型**（"帮我做 XX 游戏 / demo / 玩法原型"）→ **先过 §0（目标 = 1:1 复刻 A，不许思考、不许发挥）
  与 §4 四道前置闸门**，再读 `reference/game-delivery.md` + `patterns/game-demo.md`；
  涉及菜单/场景流转 → 必读 `patterns/client/app-flow.md`；图片 / 截图需求 → 过「图片需求硬闸门」；
  **用户没给参考游戏名 → 先问**；评估为复杂项目 → 走 `patterns/multi-agent.md`；**交付前必过 §2 的 1:1 判定**。
